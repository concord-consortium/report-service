# report-service: everything the VM calls, and the watchdog

**Jira**: https://concord-consortium.atlassian.net/browse/REPORT-143

**Status**: **Closed**

## Overview

The report-service function's `researcherDashboard` app gains the three endpoints a researcher's MicroVM calls with its own Firebase session: `POST /work`, which hands the VM its queued packages and the credentials to run them; `POST /idle`, which suspends the VM once it has nothing to do; and `POST /storage-credentials`, the storage broker, which returns AWS credentials limited to that researcher's S3 prefix and the published packages, assumed with the function's own Google identity rather than any AWS key. A new scheduled function, the watchdog, runs every minute and reconciles what a VM cannot report for itself: a run whose runner has stopped reporting, because its VM died, hung, lost its final write or was suspended mid-run, an idle VM that never asked to be suspended, and a suspended VM with work queued for it. The dashboard's Firestore tree gets its rules, with emulator tests, for the first time on this branch.

When a researcher runs packages from the dashboard, the portal already hands the work to report-service, which records it and starts or wakes that researcher's private machine (REPORT-141). This story is the other half: the machine now asks report-service for its work instead of being sent it, asks to be put to sleep when it has finished, and asks for storage credentials that reach only its own researcher's data. That last part is what lets packages written by anyone other than Concord run safely, because a stranger's package can no longer reach another researcher's student data.

It also adds a safety net. A machine that crashes, hangs, or is put to sleep in the middle of a run cannot report that anything went wrong, so the machine checks in every minute while it runs a package, and a scheduled check that runs every minute stops a machine that has gone quiet for five minutes and marks its run as failed, puts forgotten idle machines to sleep so they stop costing money, and wakes a sleeping machine that has work waiting. And it adds the database rules that decide which browser and which machine may read or write each part of the dashboard's data, so a researcher's browser can read their own results but can never see the credentials queued for their machine.

### How the VM authenticates

- **R2.** `POST /work`, `POST /idle` and `POST /storage-credentials` are routes on the `researcherDashboard` function. Each takes the VM's Firebase ID token for the function's own project in `Authorization: Bearer`, verified with the Admin SDK's `verifyIdToken`. A missing, malformed, expired or wrong-project token is 401. None of the three accepts rigse's assertion or the `api` function's shared bearer, and `/run-package` and `/derive-profile` go on accepting only rigse's assertion.
- **R3.** Before any of the three does anything, the verified token must carry `researcher_dashboard_runner` equal to `true`, `user_type` equal to `"researcher"`, a `platform_user_id` that is a positive integer or its decimal string (matching `^[1-9][0-9]*$`), and a `platform_id` that parses as an `http` or `https` URL. Anything else is 403. The researcher, the portal and `platform_id` come from the token only: `platform_user_id` names the researcher, and `{portal}` is `platform_id`'s host with dots as underscores, which is the segment `/run-package` writes under since rigse sets `iss` and `platform_id` from the same site URL (`signed_jwt.rb` `create_portal_token`; `firebase_token_claims.rb`). No body field can name another researcher or portal.
- **R3a.** **A runner session is bounded by when it signed in** (Ethan McElroy's review, 2026-10-13). A session refreshes its ID token for as long as its refresh token lives, and `verifyIdToken` does not check revocation, so the VM's first sign-in is what ends it: the token's `runner_signed_in_at` when `/work` minted it (R9), since signing in with a minted token starts a session with a new `auth_time`, and otherwise its `auth_time`, which a refresh keeps. A token with neither is 403. Each of the three answers 401 when the session signed in more than a VM's life ago (eight hours and ten minutes, the watchdog's `VM_LIFE_MS`), and 409 when it signed in more than a minute (`LAUNCH_CLAIM_MS`, which bounds a launch) before `vms/{platform_user_id}`'s `launched_at`, so a replaced VM's session is refused once its successor is recorded. The minute covers a VM signing in during `/run` before `recordLaunch` writes. A VM that ended early keeps a session that reaches its researcher's prefix until the next launch or the eight-hour bound; tying `/storage-credentials` to the recorded VM is REPORT-179, after the runner change it needs (REPORT-178).

### `POST /work`

- **R4.** `/work` answers 200 with exactly the repository's `success: true` envelope (`response-methods.ts`) and: `packages`, the researcher's queued work as `{class_hash, package_key, identity, version, checksum, catalog_id}` in queue order; `scopes`, `{<class_hash>: {scope, class_tokens}}` for the classes those packages name and no others; `session_token`; and `firebase_project`. `scope` is the block rigse sent, class list and assignments included. A researcher with nothing queued gets empty `packages` and `scopes`.
- **R5.** A package is **queued** while its result document says `queued`, and **outstanding** while it says `queued` or `running`. A missing result document counts as queued. `/work` hands out queued packages only, so a run the VM already claimed is not handed to it again after a resume.
- **R6.** `/work` is idempotent. Handing work out does not remove it, and two calls in a row return the same packages until the runner claims them by writing their results `running` (RD-4). So a VM that dies after `/work` and before claiming loses nothing, and the next VM takes the same work.
- **R6a.** `/work` takes `{microvm_id}`, the VM's own id, and answers only the researcher's recorded VM (`vms/{platform_user_id}`): a missing or non-string id is 400, and any other VM is 409 with nothing handed out. A VM the function launched and failed to record (REPORT-141's lapsed launch claim) would otherwise take the same work as the recorded one and run every package twice. The window between `RunMicrovm` returning and the launch being recorded is one transaction, so a 409 to a VM that has just booted is possible and passes; RD-4 pass 2 retries it.
- **R7.** An entry leaves `work/` when its result is `done` or `failed`. Every transaction that reads the queue drops such entries: `/work`, `/run-package`, `/idle` and the watchdog. A class's `scopes` entry is dropped with its last package. A dropped entry's result document is left alone.
- **R8.** `/run-package` (REPORT-141 as built) changes to match. A package is skipped as already queued only while it is outstanding for that class, so a re-run of a `done` or `failed` package is appended and its result written `queued` again. The cap counts outstanding packages only. `runners/{platform_user_id}`'s `queue` mirrors the queued entries, excluding any `running` one, which is what the runner reports as `current_package` instead (RD-4). REPORT-141's other behavior is unchanged.
- **R8a.** The queued result keeps the last finished run, so the page can show it while a re-run is queued or running (RD-6 pass 1, Doug, 2026-10-11). Inside the same transaction, before any write, `/run-package` reads the current result of each package it appends, and writes the queued result whole as before plus a `previous` field:
  - the current result is `done`: `previous` is its `package`, `image_version`, `summary`, `display`, `started_at` and `finished_at`, each copied when present and left out when absent (the Admin SDK refuses an `undefined` field), and never its own `previous`;
  - any other current result (`failed`, which R8 re-queues, or a status R8 cannot reach here): its existing `previous` is carried forward unchanged, and none is written when it has none;
  - no current result: no `previous`.
  No other write replaces a result whole: the watchdog's failure writes (R17, R17a) merge their named fields, and RD-4 pass 2's runner writes merge named fields too, so `previous` survives both. `display` is at most 64 KiB (RD-4's `DISPLAY_LIMIT_BYTES`), so a result holding two stays far under Firestore's 1 MiB document limit. The rules are unchanged.
- **R9.** The credentials in the response are **fresh**, which `final-design.md` 7.1(b) requires ("a freshly minted session token and the class tokens that run needs"), with one exception. `session_token`, and each class token for the function's own project (`class_tokens[<firebase_project>]`), are minted by the function when it answers, as Firebase custom tokens for the verified caller's uid carrying rigse's claims for that researcher as they reach a verifier: `platform_id`, `platform_user_id` (a number), `user_type: researcher`, `researcher_dashboard_runner: true`, and `class_hash` on a class token, all copied from the verified token except `class_hash`, which comes from the queue, plus `runner_signed_in_at`, the caller's first sign-in (R3a). rigse's `user_id` claim is not copied, because Firebase replaces it with the uid in every ID token (Technical Notes, "Checked against the emulators"), so no rule or verifier ever sees it. A class token for any other Firebase project, CLUE's, is passed through as rigse minted it, since the function cannot sign for another project, and so is good for an hour from the request that queued it. The mints are made together and bounded as one upstream call: if they have not all answered within 10 seconds, `/work` answers 502 naming the timeout rather than waiting for the function's own 60-second limit. The function mints only for the recorded VM (R6a) while its `launched_at` is within the VM's maximum life (R20), and a class token only for a class it hands work out for, so a runner token cannot be renewed past the VM that holds it or for a class rigse did not authorize in a queued request. Otherwise it passes rigse's tokens through.

### `POST /idle`

- **R10.** `/idle` takes `{microvm_id}`, the VM's own id from its `/run` hook. If the researcher has queued work, it answers 200 `{success: true, suspended: false, work_queued: true}` and suspends nothing, and the runner calls `/work`. If a `running` result names this VM in `microvm_id` (R18's test), it answers 200 `{success: true, suspended: false, run_in_progress: true}` and suspends nothing, and the runner carries on with its run; the runner never asks mid-run (RD-4 R12), so this answer means a runner bug or a run whose final write was lost, and suspending would only strand it. R17's lease fails such a result within minutes, after which `/idle` suspends. Otherwise, if `microvm_id` is the researcher's recorded VM (`vms/{platform_user_id}`), it calls `SuspendMicrovm` on it and answers 200 `{success: true, suspended: true}`. A `microvm_id` that is missing or not a string is 400, and one that is not the recorded VM is 409 with nothing suspended, so a stray VM cannot suspend the researcher's current one. `SuspendMicrovm` failing or timing out is 502 with the reason.
- **R11.** `/idle` writes no status document: the VM's own `/suspend` hook writes `suspending` and `suspended`. Work queued between the check and the suspend lands on a `SUSPENDING` VM, which `/run-package` leaves alone and the watchdog resumes (R19).

### `POST /storage-credentials`, the storage broker

- **R12.** The broker calls STS `AssumeRoleWithWebIdentity` directly on the runner stack's broker role, which a new setting names (R26), with no role chain and no AWS key: the web identity token is a Google ID token the function's own service account mints for `RD_AWS_AUDIENCE` for this call, never reused. The call has `DurationSeconds` 3600, `RoleSessionName` `researcher-<platform_user_id>`, no `PolicyArns` and no `ProviderId`, and `Policy` set to this session policy, minified, `<bucket>` being `RD_DATA_BUCKET` and `<id>` the verified `platform_user_id` (`speccing.md`, "The storage broker's contract for REPORT-143"; RD-1 R12):

  ```json
  {"Version":"2012-10-17","Statement":[
    {"Effect":"Allow","Action":"s3:ListBucket","Resource":"arn:aws:s3:::<bucket>","Condition":{"StringLike":{"s3:prefix":"researchers/<id>/*"}}},
    {"Effect":"Allow","Action":["s3:GetObject","s3:PutObject","s3:DeleteObject"],"Resource":"arn:aws:s3:::<bucket>/researchers/<id>/*"},
    {"Effect":"Allow","Action":"s3:GetObject","Resource":"arn:aws:s3:::<bucket>/packages/*"}
  ]}
  ```

- **R13.** The broker refuses to mint unless `<id>` matches `^[1-9][0-9]*$` (R3 already refuses the request), and unless the bucket is a valid S3 bucket name, which contains no `*` or `?`; both are checked before a token is minted. No code path assumes the broker role without the session policy: the broker's one call builds the policy itself from the id and the bucket, so no caller can leave it out; the broker role setting is handed to that call and to nothing else, so the launcher's credential provider, which passes no policy, can never be pointed at it; and no STS client exists anywhere in the function.
- **R14.** It answers 200 `{success: true, access_key_id, secret_access_key, session_token, expiration, bucket, prefix, region}`, where `expiration` is STS's expiry as an ISO 8601 string, which the runner checks against the wall clock before each use; `prefix` is `researchers/<id>/`; and `region` is `us-east-1`. While the broker role setting, `RD_DATA_BUCKET` or `RD_AWS_AUDIENCE` is empty it answers 503 naming them, and while `RD_DATA_BUCKET` is not a valid bucket name it answers 503 saying the broker is misconfigured (both Doug, 2026-09-25). It answers 502 with the reason when the ID token cannot be minted, when STS refuses, or when the two together take more than 10 seconds. Nothing is retried: the STS call is made once (`maxAttempts` 1).
- **R14a.** In the emulator the broker refuses with 502 and makes no call, whatever `RD_EMULATOR_AWS` says: the emulator has no service account, and a session from the developer's own credentials would not be the function's (`final-design.md` 11.4, "The emulator").
- **R15.** *(the live check is built; its run against each stack is a rollout step not yet taken; see Not Yet Implemented)* The broker is tested two ways. Unit tests assert the exact policy for a given bucket and id, that every broker call carries it with `DurationSeconds` 3600 and a freshly minted token for the stack's audience, that ids like `*`, `1*`, `?`, `0`, `-1`, `1.5` and the empty string are refused before a token is minted, and the source guard of R13. A live check, run by an operator against a stack, drives the function's own broker code with the account's ID tokens for the stack's audience, minted for the operator by the setup script's `id-token` subcommand (R27b), the operator holding OpenID Token Creator on the account from the setup script's `grant-operator` and losing it with `revoke-operator` afterward, and no AWS credential of their own (Q12). It prints the account, audience and role before any call, and asserts with real calls that one researcher's session cannot read or list another researcher's existing object, can read a published archive, cannot write, delete or list under `packages/`, and can read, write, list and delete its own prefix. The live check is a required rollout step (Doug, 2026-09-25): it runs against each stack after this story's deploy and must pass before RD-4 pass 2's runner, the first that syncs with broker credentials, is released to that stack, and its result is recorded against this spec. CI runs only the unit tests, since it holds no Google or AWS credential. No `packages-read` check precedes the deploy: RD-1 is one pass, so `BrokerRole` holds `packages-read` from the stack's creation (`speccing.md`, "The storage broker's contract for REPORT-143").

### The watchdog

- **R16.** A scheduled function, `researcherDashboardWatchdog`, runs every minute in the same project as `researcher-dashboard@<project>`, the account `researcherDashboard` runs as, reaching the MicroVM API through the same launcher credential provider and holding no secret, and uses the Admin SDK. Each run makes the passes below, checks its budget before every upstream call (a `TerminateMicrovm` right after a `GetMicrovm` included) and starts none after 30 seconds, and makes each upstream call once with a 10-second timeout. A call may first refresh the launcher's AWS credentials, which `aws-credentials.ts` bounds at 10 seconds of its own, so one call can take 20 seconds, and a call started at 30 seconds and its conditional write still finish inside the function's 60. A `TerminateMicrovm` is followed by no write, and a wake's one write comes before its `ResumeMicrovm` (R19). A failure on one document or VM is logged and does not stop the rest. Two runs overlapping do no harm: each result write is conditional on the result being unchanged since it was read.
- **R17.** **Lost runs: a heartbeat lease, kill then fail** (Q13, Doug, 2026-10-13). While a runner holds a package it rewrites the result's `updated_at` every `heartbeat_seconds` (RD-4 pass 2), and the claim records `heartbeat_seconds` (R22a). A `running` result's quiet time is now, on the function's clock, minus the later of its `updated_at` and, when `vms/{platform_user_id}` records the same VM as the result's `microvm_id`, that document's `resumed_at` (R19). The result is stale once its quiet time exceeds five times its `heartbeat_seconds`, which is 5 minutes at RD-4's 60. The same-VM tests here and in the moved-on case compare the id the runner writes with the one `RunMicrovm` returned, which `recordLaunch` stores in `vms/` and on the runner document, so they hold only while RD-4 pass 2 writes `microvm_id` in `RunMicrovm`'s form, as R19a's guard does. A result whose `heartbeat_seconds` is not an integer from 30 to 120 is skipped: the rules refuse such a claim, so only an Admin SDK write could leave one. A result whose lease still holds, because a recent `resumed_at` restarted it, is also considered once it is past the `SUSPENDED` bound below, which reads `updated_at` alone, but only that branch acts on it. A stale result is handled in this order:
  - **The runner has moved on**: `runners/{platform_user_id}` records the result's VM, its `state` is neither `terminated` nor `failed`, its `current_package` is not this result (class and package key), and its `updated_at` is later than the result's. A terminal state means the VM is ending or gone, which the branches below handle and log as such. The result is failed, and no VM is asked about or touched. RD-4 pass 2 writes nothing after a run until that run's final write has settled, meaning the SDK's write promise has resolved or rejected, never a local timeout, since a write the runner stopped waiting for can still land; and every runner-document write while a run is outstanding, the `/suspend` and `/terminate` hooks' included, keeps `current_package` naming that run. So a runner that has written its document since will never write this result again; this is the run whose final write was refused or lost, and killing the VM would take down a healthy run or a warm idle VM.
  - Otherwise `GetMicrovm` on the result's `microvm_id`, which the rules require on every `running` result. A pass asks about each VM at most once, and an answer that finds the VM but carries no `state` is logged as an upstream failure and left for a later pass, as a failed call is, since that VM may be live:
    - not known, or `TERMINATED`: the result is failed.
    - `TERMINATING` or `SUSPENDING`: nothing. An awake VM being terminated runs its `/terminate` hook, which can write this result for up to 60 seconds while the VM reports `TERMINATING` (`design.md` criterion 11), and a failure the watchdog wrote first could be re-queued by the researcher and then overwritten by the hook. A later pass acts once the VM is gone.
    - `PENDING` or `RUNNING`: the VM is terminated with `TerminateMicrovm` and nothing is written. A later pass fails the result once the VM is gone, unless the hook already has.
    - `SUSPENDED`: only once now minus the result's `updated_at` alone also exceeds `expected_duration_seconds` (capped at 28,800, taken as 28,800 when absent) plus a 10-minute margin, the VM is terminated and nothing is written; a later pass fails the result. Before that, nothing: a suspended VM sends no heartbeat, and RD-3's Resume can still finish the run. `resumed_at` is left out of this bound because R19 writes it before each `ResumeMicrovm`, so a resume that keeps failing would otherwise postpone it forever; a resume that succeeds restarts the lease, and the run's beats then move `updated_at`.

  Every failure here writes the one reason "The machine running it stopped before the run finished; run it again.", merges `status`, `error`, `finished_at` and `updated_at` and nothing else, so `previous` (R8a) survives, and happens only if the result is still `running` with the `updated_at` the watchdog read. When the VM is gone, `runners/{platform_user_id}` is also written `state: terminated` with `current_package` cleared, but only while its `microvm_id` is that VM and its `state` is neither `terminated` nor `failed`, as in R19a, so a document a newer VM has taken over is left alone and a `failed` the `/terminate` hook wrote after an incomplete flush keeps its reason; the moved-on case leaves the runner document to the live runner. A `TerminateMicrovm` that fails, including on a VM an overlapping run has just terminated, is logged as an upstream failure and writes nothing. The results are found by the collection-group query on `status: running` and `updated_at` older than five times the smallest `heartbeat_seconds` the rules allow, 150 seconds, on the existing index, and each document's own threshold is applied in code. A run lost on an awake VM therefore reads failed about 7 to 9 minutes after its runner goes quiet.
- **R17a.** **Work no VM took.** A result with `status: queued` whose `updated_at` is more than eight hours and ten minutes old, for a researcher whose VM in `vms/{platform_user_id}`, if any, was also launched more than eight hours and ten minutes ago and who has no launch under way (`launching_until` still in the future), is written `failed` with the reason "No VM took this package before its VM's life ended; run it again". By then every VM that could have claimed it is gone, so without this the entry stays queued forever: `/idle` reports `work_queued`, R18 keeps every later VM awake to its cap, and a re-run is skipped as already queued. The write follows R17's rule (only those fields, only if the result is still `queued` with the `updated_at` read), touches no runner document, and makes no upstream call; R7 then prunes the entry.
- **R18.** **Idle VMs.** For each VM launched within its maximum life (eight hours, plus a margin) that `GetMicrovm` reports `RUNNING`: if the researcher has nothing queued and no `running` result that this VM claimed (one naming it in `microvm_id`), the runner document's `current_package` is empty or names a result that is not `running` on this VM, and nothing has happened for 30 minutes (the latest of the runner document's `updated_at`, the work document's `updated_at` and the launch), the VM is suspended with `SuspendMicrovm`. That covers a VM that dies without calling `/idle`, and the runner's own idle period must be well under 30 minutes (RD-4).
- **R19.** **Work queued behind a suspend** (REPORT-141 R16). For each VM in the same set that `GetMicrovm` reports `SUSPENDED` while the researcher has queued work, the VM is resumed with `ResumeMicrovm`. Work queued while a VM was suspending therefore waits about a minute. This deliberately narrows REPORT-141's clause from outstanding work to queued work: a `running` result's VM is awake, or suspended mid-run, where R17 bounds it and RD-3's Resume is the researcher's choice, so the watchdog never resumes for one. The watchdog and `ensureVm` decide to wake a suspended VM through one shared function, given the VM's recorded `image_version`, so a later rule about which VMs to wake (REPORT-170) lands in one place. Before it calls `ResumeMicrovm`, that function writes `vms/{platform_user_id}`'s `resumed_at`, a server timestamp, in a transaction that writes it only while the document still records that VM; once it records another VM, nothing is resumed, since that VM is the one to take the work. The watchdog's budget is checked again after that write, just before `ResumeMicrovm`, and a VM that R17 terminated earlier in the same pass is not resumed. A run continued by the resume has an `updated_at` from before the suspend, and without this R17's lease would kill it at the first pass; written before the call, no pass can see the VM `RUNNING` with only the old time. A resume that then fails leaves the VM `SUSPENDED`, whose bound in R17 reads `updated_at` alone. The watchdog never launches a VM: a launch mints the researcher's report-server token from the portal assertion that only a run request carries, and `work/` does not keep it.
- **R19a.** **Runner documents a dead VM left behind** (Doug, 2026-10-13). For each VM in the same set that `GetMicrovm` does not know, or reports `TERMINATED`, `runners/{platform_user_id}` is written `state: terminated` with `current_package` cleared and its `queue` kept, but only while its `microvm_id` is that VM and its `state` is neither `terminated` nor `failed`, the two terminal states. Without this, a VM that fails `/run` after the runner wrote `starting` (RD-4 pass 2: no `microvmId`, the token claims, the credential fetch, the pull-down), a stale `ready`, a `suspended` VM that reached its 8-hour cap (`final-design.md` 7.3), or one R17 terminated while suspended, which runs no `/terminate` hook, leaves the document claiming a live session, which RD-3 pass 2 reads as "the session will take it" until R17a fails the queued work at 8 hours 10 minutes. RD-3 pass 2 renders `terminated` as "run it to start one", and the researcher's next run launches a VM that takes the kept queue. The pass makes no upstream call beyond the `GetMicrovm` it already makes, the write goes in the pass's own transaction, after its reads, and the terminal-state guard stops it rewriting the same document every minute while the VM stays in the set. `TERMINATING` is left alone, as in R17: an awake VM's `/terminate` hook writes the runner document itself, and the next pass acts once the VM is gone. It does not fail a `running` result naming that VM: R17 does that on the same pass. The guard compares with `vms/`'s id, which `recordLaunch` also writes onto the runner document, so it holds only while the runner writes its id in the same form.
- **R20.** The VMs are found from `vms/{platform_user_id}`, which gains `launched_at`, a server timestamp written when the launch is recorded (REPORT-141's `recordLaunch`), and `resumed_at`, written by the shared wake (R19) and set to null by `recordLaunch`, so a new VM never carries the last one's. A VM recorded before this story's deploy has none and is not swept; it is gone within eight hours of its launch in any case (`maximumDurationInSeconds` is how long "the MicroVM can exist", in the SDK's words, and the function launches with 28,800). The stalled runs are found by a collection-group query on `results`. Both queries have their indexes in `firestore.indexes.json`, and any document outside `researcher_dashboard/{portal}/...` that a collection-group query returns is ignored.
- **R21.** Every action the watchdog takes is logged as one structured line naming the action, the researcher, the portal, the VM and, where there is one, the package and class: a result failed, a VM terminated, suspended or resumed, a runner document marked terminated (R19a), and an upstream failure. The line's message is its event name, one of `watchdog.result_failed`, `watchdog.vm_terminated`, `watchdog.vm_suspended`, `watchdog.vm_resumed`, `watchdog.runner_terminated` and `watchdog.upstream_failed`, so a log-based metric can count any of them later. `watchdog.vm_terminated` carries `reason`, `lease` or `suspended_mid_run`, and `watchdog.result_failed` carries `cause`, `moved_on`, `vm_gone` or `not_claimed`, so the one reason the researcher sees does not hide why the watchdog acted. ### The rules for the dashboard's Firestore tree

- **R22.** `firestore.rules` gains a `researcher_dashboard/{portal}` block, per `final-design.md` 9:
  - Every rule requires an authenticated token whose `platform_id` host, split into labels, equals `{portal}` split on `_`.

No `delete`, no `list`.

No `delete`.
  - `…/results/{package_key}`: the same as its parent, plus `list` for that researcher of that class.
  - Reads are `get` and `list`, and writes are `create, update`, never `read` or `write`. Nothing grants a delete.
- **R23.** The runner claim is read with `.get("researcher_dashboard_runner", false)`, since a bare read of an absent claim is an evaluation error that denies every token (`spike-plan.md` 12).

- **What a terminated VM writes, and when** (`10-13-2026-orphaned-run-analysis.md`). Terminating an awake VM runs RD-4's `/terminate` hook while `GetMicrovm` reports `TERMINATING`: it writes the outstanding run's result `failed` with an unconditional merge, revokes the report-server token, flushes, and writes the runner document, within the hook's 60 seconds (`runner.js` `terminate`; `design.md` criterion 11). A VM terminated while suspended runs no hook (`final-design.md` 7.3). So R17 and R19a act only on not found or `TERMINATED`, and the result's last writer is either the hook or the watchdog, never both in the wrong order.
- **The runner's side of the lease (RD-4 pass 2).** The claim writes `heartbeat_seconds: 60`. While a package runs, the runner merges `{platform_id, updated_at}` into the result every 60 seconds through the run's own store, skips a beat while the previous one is unsettled, and stops the timer and awaits any beat in flight before the final write, so a beat never bumps a finished result's `updated_at`, which RD-6 keys on. The run's Firebase app stays open until the final write settles, the SDK's write promise resolving or rejecting, never a local timeout, and the runner writes nothing else, the runner document included, until it does. Every runner-document write while a run is outstanding, the `/suspend` and `/terminate` hooks' included, keeps `current_package` naming that run. Those two rules are what make R17's moved-on case safe. The runner writes `microvm_id` in `RunMicrovm`'s form, on the result and the runner document, since R17's same-VM tests and R19a's guard compare it with `vms/`. The `/terminate` hook's result write uses R17's one reason. 3.2a's `idleSince` reset on a `run_in_progress` answer stays, as does the in-VM package timeout, since a hung package keeps heartbeating. Its QA release (`landing-tracker.md` 3.4) checks: a VM terminated mid-run, with `GetMicrovm`'s states recorded against the hook's log; a run longer than 65 minutes, since the heartbeat depends on the SDK refreshing its token at the hour; a suspend mid-run resumed from the dashboard; and `design.md` criterion 11 again. The `/terminate` hook writes the runner document in a transaction that writes only while the document records this VM, so a researcher who runs again within the hook's 60 seconds of a kill does not have the new VM's document overwritten.
- **`/storage-credentials` does not check the recorded VM's id.** One set of credentials lasts an hour, but the session that asks can outlive its VM, so the route applies R3a's bound and takes no `microvm_id`, unlike `/work` (R6a). The runner fetches credentials during `/run`, before its first `/work`, with rigse's session, which carries no VM claim; a claim check waits for REPORT-178 and REPORT-179.
- **An accepted risk in R17's moved-on case.** `/run-package` bumps the runner document's `updated_at` on every request. If a claim's result write lands but its runner document write is lost, and the run's beats then fail for five minutes while the run is still alive, a request in between makes the run look moved on, and it is failed without a kill; the live runner's later write could land on a re-queued result. That takes two independent write failures and a re-run inside minutes, and is left to RD-4 pass 2's staging checks.
- **What RD-3 pass 2 sees.** No code change: a lost run's row reads failed with R17's reason about 7 to 9 minutes after its runner goes quiet, and a killed VM's runner document reads `terminated`, which renders as "run it to start one". Its staging check's timing for a lost run changes from hours to minutes.

## Decisions

### Q1. Does the function mint `/work`'s tokens, or pass rigse's through?
**Context**: `final-design.md` 7.1(b) says every `/work` response carries "a freshly minted session token and the class tokens that run needs". Minting needs a signing grant the function's account lacks by default (Technical Notes, "Signing `/work`'s tokens"). rigse mints the tokens when a run is requested, and a custom token cannot be exchanged more than an hour after it is minted. Every resume follows a request or the watchdog's resume of work queued during a suspend, so the latest tokens are minutes old then. The case that breaks is a long queue: a researcher queues a two-hour package for class A, then a package for class B ten minutes later. The runner learns of B's package at its next `/work`, after A's finishes, and B's tokens are then 110 minutes old, so it cannot sign in to write B's result.
**Options considered**:
- A) Pass rigse's tokens through. No infrastructure change. The long-queue case fails at the runner's sign-in, and RD-4 pass 2 has to report it as a failed run naming the reason.
- B) The function mints the session token and its own project's class tokens on every `/work`, copying the identity claims from the verified caller (R9), and passes CLUE's class tokens through. Each project needs the IAM Service Account Credentials API enabled and the function's account granted `roles/iam.serviceAccountTokenCreator` on itself, which is an operator's change outside any repository. The long-queue case then fails only for a package that also pre-pulls CLUE, and RD-5 retires that token.
- C) B, but signing with a service-account key held as a function secret. No API or IAM change, and a long-lived key to guard and rotate.

**Recommendation**: B. It is what the design says, it makes every report-service write the runner makes sign in with a token minted seconds before, and the grant is on the function's own account in its own project, which already writes every document the tokens could. R9 and the implementation spec are written for B; under A, R9 becomes "passed through as rigse minted them".

**Decision**: B (Doug, 2026-09-25). The function mints the session token and its own project's class tokens on every `/work`, and passes CLUE's through. It signs as `researcher-dashboard@<project>`, which needs `roles/iam.serviceAccountTokenCreator` on itself and the IAM Service Account Credentials API enabled, both from the setup script (R27a), before RD-4 pass 2's runner is released.

### Q2. Should the rules enforce the write contract the watchdog relies on?
**Context**: The watchdog reads three fields the runner writes when it claims a package: `updated_at`, `expected_duration_seconds` and `microvm_id` (R17). Firestore compares a range only against values of the same type, so a result whose `updated_at` is an ISO string, as the spike runner writes today, is invisible to the stalled-run query and never failed. A client-supplied timestamp also comes from the VM's clock, which is not real after a suspend (`final-design.md` 7.1), so a resumed VM could stamp a fresh run with a time that makes it look stalled, or a stalled one look fresh. Adding the constraint changes what RD-4 pass 2 must write, which is a contract another story consumes.
**Options considered**:
- A) The rules require every runner write to `runners/…` and `…/results/…` to set `updated_at` to the server's time (`request.resource.data.updated_at == request.time`, which the client SDK's `serverTimestamp()` satisfies), and a write of a result as `running` to carry `expected_duration_seconds` as an integer from 1 to 28,800 and `microvm_id` as a string. Emulator tests cover each refusal.
- B) Record the contract for RD-4 pass 2 and leave the rules as `final-design.md` 9 states them.

**Recommendation**: A. It turns two silent failures of the watchdog into a refused write the runner sees at once, it takes the VM's clock out of every threshold, which is the design's rule, and it costs RD-4 pass 2 only the use of `serverTimestamp()`, which it needs for Firestore timestamps anyway.

**Decision**: A (Doug, 2026-09-25). The rules require a server-time `updated_at` on every runner write to `runners/…` and `…/results/…`, and `expected_duration_seconds` (an integer from 1 to 28,800), `microvm_id` (a string) and, since Q13, `heartbeat_seconds` on a result written `running`. Recorded as R22a.

### Q5. When does an entry leave `work/`, given nothing removes one today?
**Context**: Background, "Nothing ever leaves `work/`". Three shapes were considered: `/work` takes the work and removes it; the runner reports completions in its next call; or the queue is pruned by the status the runner already writes on each result.
**Decision** (from the code): pruned by result status (R5 to R8). A take loses work if the VM dies between `/work` and its claim, and leaves the page showing work nobody holds. A completion report adds a field to every runner call and trusts it. Result status is written by the runner on every claim and finish, by the watchdog when it fails a run, and read by the function with the Admin SDK in the same transaction that reads the queue, so nothing new is written and no work can be lost. The cost is reading up to 20 result documents per transaction, the cap's size.

### Q6. Which VM does `/idle` suspend?
**Decision** (from the code): the one the caller names, and only if it is the recorded one (R10). The runner knows its own id (`runner.js`, `run({ microvmId })`). Suspending the recorded VM without the check would let a stray VM, which REPORT-141's lapsed launch claim can leave, suspend the researcher's current VM mid-run.

---

### Q7. How does the watchdog find the VMs to sweep?
**Context**: `final-design.md` 7.2(c) sweeps "a session", which could be read from the runner documents, whose `state` a dead VM leaves stale, or from `vms/`, which accumulates one document per researcher ever.
**Decision**: from `vms/` launched within the last eight hours and ten minutes (R20), so the set is the researchers with a VM that can still exist, however many researchers there have ever been. `get-microvm` is the authority on state (`final-design.md` 7.3), so the runner document is read only for `current_package` and `updated_at`.

---

### Q8. What does the watchdog write to the runner document when a VM is gone?
**Decision**: `state: terminated`, with `current_package` cleared and the queue kept, once `GetMicrovm` no longer knows the VM or reports it `TERMINATED`, and only while the document records that VM (R17, R19a); terminating a VM writes nothing. `final-design.md` 7.3 notes that a suspended VM that is terminated leaves the document saying `suspended` for a VM that no longer exists. The watchdog is the one component that sees every recorded VM's state, and the page renders from that document. The queue is kept, since the work is still queued and the researcher's next request launches a VM that takes it.

---

### Q9. The idle sweep's threshold, and the stalled-run margin
**Decision**: 30 minutes of nothing for an idle VM, and 10 minutes past a run's declared duration for a VM suspended mid-run (an awake VM's run is judged by the heartbeat lease, Q13), both constants in the code rather than params. Neither number is in the design. 30 minutes leaves the runner's own idle period (RD-4's setting) room to act first, and costs at most about $0.13 of running time for a VM that died. 10 minutes is well above the spacing of the runner's result writes and below any declared duration worth waiting on. Each is one constant to change.

### Q12. How does an operator mint the account's ID token for a live check?
**Context**: The keyless plan gives operators OpenID Token Creator on the function's account for live checks, deliberately not Token Creator, "which also mints access tokens and signs blobs" (`oidc-launcher-plan.md`, "Operators and manual checks"; `final-design.md` 11.4), and mints the check's token with `gcloud auth print-identity-token --impersonate-service-account=… --audiences=…` (the same plan, RD-1 R20 and its README's `assume` helper, and this story's re-spec brief). gcloud 583.0.0's impersonation always mints an access token for the account first (`googlecloudsdk/core/credentials/store.py` `Load` calls `GetElevationAccessTokenGoogleAuth`, which refreshes `google.auth.impersonated_credentials.Credentials`) and only then the ID token, so it needs `iam.serviceAccounts.getAccessToken`, which OpenID Token Creator does not grant. Run on 2026-10-07 as `developer@concord.org`, holding neither role, the command was refused on `iam.serviceAccounts.getAccessToken`, while a direct `POST https://iamcredentials.googleapis.com/v1/projects/-/serviceAccounts/researcher-dashboard@report-service-dev.iam.gserviceaccount.com:generateIdToken` with the operator's own access token was refused on `iam.serviceAccounts.getOpenIdToken`, the one permission OpenID Token Creator carries.
**Options considered**:
- A) Mint with `generateIdToken` directly, keeping operators at OpenID Token Creator. This story's live check already does (R15). RD-1's `assume` helper becomes `TOKEN=$(curl -s -X POST -H "Authorization: Bearer $(gcloud auth print-access-token)" -H 'Content-Type: application/json' https://iamcredentials.googleapis.com/v1/projects/-/serviceAccounts/$SA:generateIdToken -d "{\"audience\":\"$STACK\"}" | jq -r .token)`, and the plan, `final-design.md` 11.4 and `speccing.md` name that call instead of the gcloud flag.
- B) Keep `gcloud … --impersonate-service-account` and have `grant-operator` grant Token Creator for the check, which also lets the operator mint access tokens as the account and sign blobs (and so sign Firebase custom tokens) until it is revoked.

**Recommendation**: A. It keeps the narrower grant the design chose on purpose, it is one HTTP call.

**Decision**: A, as one command (Doug, 2026-10-07: "this seems like a footgun"). The obvious command fails with an error that says to grant Token Creator, which would quietly undo the narrow grant, so the fix removes the choice rather than documenting around it: the setup script's `id-token` subcommand is the only way an operator mints the account's token (R27b), this story's live check calls it, and RD-1's `assume` helper, `oidc-launcher-plan.md`, `final-design.md` 11.4 and `speccing.md` name it instead of the gcloud flag.

### Q13. What ends a `running` result whose runner has stopped reporting?
**Context**: A result can stay `running` with nobody working on it: both final writes lost or refused, a runner crash, a runner bug. Judged only past `expected_duration_seconds` plus 10 minutes, and never on an awake VM, such a result would read "running" for up to 8 hours, `/idle` would keep the VM awake for it, and RD-3 would not call it stuck. Two analyses are in `10-13-2026-orphaned-run-analysis.md`.
**Options considered**:
- A runner-only retry before `/idle`. Rejected: misses refused writes, crashes and bugs.
- Failing a run on an awake VM past its declared duration. Rejected: a declared duration is brittle.
- A heartbeat lease that fails the result. Needs a run id guard, since the still-live runner's late `done` could land on a result the researcher has re-queued.
- A heartbeat lease that terminates the VM and fails the result once the VM is gone (kill then fail). No live runner is left to write late, so no guard.

**Decision** (Doug, 2026-10-13, `landing-tracker.md`, Open decisions item 2a): kill then fail. (1) A VM suspended mid-run keeps the declared duration plus 10 minutes, then is terminated and the run failed on a later pass; the lease applies to awake VMs and restarts at each resume. (2) A runner that has moved on gets the stale result failed without a kill. (3) No run id guard. (4) The rules require `heartbeat_seconds` on every claim, an integer from 30 to 120, with no fallback. (5) 60-second beats and a lease of five beats. (6) One reason for every lost-machine failure, from the watchdog and the runner's `/terminate` hook, "The machine running it stopped before the run finished; run it again."; the log records why. Recorded as R16 to R22a.
