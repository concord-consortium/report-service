# Mint Scoped Portal Tokens for the Pipeline's Portal Calls

**Jira**: https://concord-consortium.atlassian.net/browse/REPORT-83
**Repo**: https://github.com/concord-consortium/report-service
**Implementation Spec**: [implementation.md](implementation.md)
**Status**: **In Development**

> **Re-scope note (supersedes the abandoned "forward the student's identity" design).** The original
> REPORT-83 had report-service forward the student's Firebase JWT in an `X-Portal-Student-JWT` header
> so the portal would *act as the student*, gated by per-feature capabilities. That was set aside
> after RIGSE PR review. The replacement, **RIGSE-352 (OIDC-Minted Scoped Portal Tokens)**, moves all
> elevation to one mint endpoint: report-service exchanges the student's forwarded Firebase token for
> a **scoped portal JWT** and then makes ordinary portal calls **as the least-privileged teacher** of
> the student's class, against existing endpoints. This spec is the report-service half of that
> design, which RIGSE-352's "Out of Scope" names explicitly: *"calling `oidc_mint` per scope and
> switching steps to the returned portal token."*

## Overview

When a student clicks the "I'm Done" button, the report-service pipeline calls back into the portal to enroll the student into a class, lock the pre-test offering, and notify the teacher. Today those calls authenticate with a Google OIDC service token that the portal maps to one fixed privileged user, so every action runs as that shared account. This story (a) adds the report-service infrastructure to obtain a **scoped portal JWT** from the portal's mint endpoint (`POST /api/v1/jwt/oidc_mint`), exchanging the student's already-in-hand Firebase token for a token that acts as the least-privileged teacher of a class, cached per run in a **map keyed by scope and class**; and (b) **cuts the existing spring-2026 pipeline's three portal calls over** to that flow, so the live pipeline stops acting as the shared admin and acts as the class's teacher instead. The new fall pipelines and their steps consume this same infrastructure but are built in sibling stories.

## Project Owner Overview

This is the report-service half of the "I'm Done" button portal-authentication change (epic DT-20), pairing with **RIGSE-352** (the mint endpoint, the `send_class_teachers` teacher-notification endpoint, and the `can_mint_scoped_tokens` opt-in flag). The button's user-facing behavior does not change; what changes is that each portal action becomes attributable to a specific, auditable minted teacher identity scoped to the student's class, instead of running as one broadly privileged shared account. It delivers reusable pipeline infrastructure (a future pipeline mints the identity it needs and calls existing endpoints, with no new portal work) and, in the same story, moves the production spring-2026 pipeline onto it. It is a blocking dependency for the fall RCT pipelines (REPORT-82). One operational change worth confirming with the study team: the teacher notification now goes to every teacher listed on the student's origin class, rather than to the single shared study account it used before.

## Background

The "I'm Done" pipeline lives in `report-service/functions/` and runs as an asynchronous Cloud Task. When the student clicks the button, the Activity Player host POSTs to `submitTask` with the student's Firebase JWT in `Authorization: Bearer`; `submitTask` forwards that JWT into the Cloud Task payload, and `taskWorker` routes to the `ai4vs-flvs` pipeline (`functions/src/tasks/ai4vs-flvs/index.ts`). The JWT is placed on `StepContext.firebaseJwt` (validated non-empty in `index.ts`) and is already used to read the student's own answers from Firestore via `getClientFirestore(firebaseJwt)` (it is the portal-minted **custom** Firebase token).

The pipeline makes three portal calls, all through the shared helper `portalOidcFetch` (`functions/src/tasks/portal-api.ts`), which today mints a Google OIDC ID token and sends it as `Authorization: Bearer`; the portal maps that token to one fixed `Admin::OidcClient.user`, so every action runs as one privileged mapped user:

1. **Enroll** into a class: `POST /api/v1/students/add_to_class` with `{ user_id, clazz_id }`, where `clazz_id` is the randomized destination (`treatment_class_id` / `control_class_id` authored params) (`random-assignment.ts:396-405`).
2. **Lock the pre-test**: `PUT /api/v1/offerings/{resource_link_id}/update_student_metadata` with `{ user_id, locked }`, acting on the student's origin offering (`lock-activity.ts:30`).
3. **Notify the teacher**: `POST /api/v1/emails/oidc_send` with `{ subject, message }` (`send-email.ts:65`); in production this emails the mapped user (the study teacher).

Under the new design the OIDC service token is used **only to authenticate the mint call**. The mint returns a scoped portal JWT, and the three calls are then made with that **portal token** (the `jwt_bearer_token` path), acting as the appropriate class's teacher.

### Cross-repo contract (source of truth: RIGSE-352, design approved, in code review)

Confirmed against the RIGSE-352 code (`oidc_mint_controller.rb`, `emails_controller.rb`, `lib/forwarded_firebase_token.rb`, `config/routes.rb`, `api_controller.rb`). The error envelope is **not uniform**: the `error(...)` helper (used by the mint's forwarded-token failures and by the email validation failures) renders the full `{ success: false, response_type: "ERROR", message, details? }`, but the two framework handlers render a thinner shape without `response_type` or `details`: `pundit_user_not_authorized` returns `{ success: false, message: "Not authorized" }` (so the `send_class_teachers` `class_teacher?` denial, a Pundit `403`, has no `details`), and `parameter_missing` returns `{ success: false, message }` (a missing `class_id` `400`). The classifier must therefore branch on **HTTP status** for the downstream `403` and the missing-param `400`, and rely on `details.reason` only for the mint `422`. RIGSE-352 is still in code review, so re-verify the exact param names/shapes against it as merged before this story deploys (see Blocked On).

**Mint endpoint** `POST /api/v1/jwt/oidc_mint`:
- Auth: the existing **OIDC bearer** service token (`Authorization: Bearer <OIDC token>`); the OIDC client must have `can_mint_scoped_tokens = true`.
- Params: `firebase_token` (required, the forwarded student token verbatim = `StepContext.firebaseJwt`), `token_type` (required, `"teacher"` for this pipeline; `"learner"` exists but is unused), `class_id` (optional, for a **cross-class** teacher mint; omitted means the student's origin class), `description` (optional, an audit label of pipeline + mint scope, e.g. `spring-2026:origin` / `spring-2026:class-12345`; sanitized server-side to 100 chars with newlines stripped, then both logged and embedded as the token's `minted_for` claim).
- Success: `201 { "token": "<signed portal JWT>" }`.
- Failure (sends nothing): `422` with `details.reason` when the forwarded token fails verification (reasons: **`expired`** [the one terminal reason], `signature`, `app_not_allowed`, `platform_id`, `not_learner`, `user_unresolved`, `offering_unresolved`, `clazz_unresolved`, `class_hash_mismatch`, `app_not_found`, `no_iss`, `undecodable`); `422` (no `details.reason`) for a bad `token_type`, an unresolvable `class_id`, no shared teacher between origin and target class, or an origin class with no teacher; `401` when the request has no resolvable user at all (`require_api_user!` fires before `require_token_minter!`, so an OIDC token that fails to authenticate as a user returns `401`, not `403`); `403` when a user *is* authenticated but not via the OIDC bearer strategy, or the client lacks `can_mint_scoped_tokens`. Both `401` and `403` are config/auth failures retry cannot fix and share the "tell your teacher" bucket.
- The mint derives the subject only from the verified Firebase token, chooses the **least-privileged** teacher, and stamps audit claims on the token. A minted teacher token is **not** class-scoped: it acts as that teacher across all of that teacher's classes.

**Teacher-notification endpoint** `POST /api/v1/emails/send_class_teachers` (this replaces the `oidc_send` call; the earlier `oidc_teacher_send` name is obsolete):
- Auth: a **portal teacher token** (the minted teacher JWT via `jwt_bearer_token`), not OIDC. Unlike `oidc_send`, this endpoint is explicitly OIDC-exempt (`skip_before_action :require_oidc_auth!, only: [:send_class_teachers]`), which is why it accepts the minted teacher token instead of rejecting it for lacking OIDC.
- Request: `{ class_id (required), subject (required string), message (required string) }`; emails **all** non-blank teacher emails of that class; no caller-supplied recipient.
- Authorization: the acting teacher must be a teacher of `class_id` (Pundit `send_class_teachers?`, which delegates to `class_teacher?`).
- Failure (sends nothing): `400` (missing/unresolvable `class_id`), `403` (not a teacher of the class), `422` (no non-blank teacher email, or non-string subject/message), `502` (delivery). Success: `200 { success: true, message: "Email sent" }`. Note the `subject`/`message` `param.require` runs *after* the class lookup, authorization, and recipient check, so an absent subject/message returns `400` (`ParameterMissing`, thin shape) while a present-but-non-string value returns `422`; report-service always sends both, so the `400` path is unreachable from this pipeline and the classifier's status-based bucketing covers it regardless.

**Enroll and lock** use the returned teacher token against the existing, unchanged `add_to_class` and `update_student_metadata` endpoints.

## Requirements

### Minting and token management (infrastructure)

- Add report-service infrastructure to obtain a scoped portal JWT by calling `POST /api/v1/jwt/oidc_mint` with the OIDC service token as `Authorization: Bearer`, `firebase_token = StepContext.firebaseJwt` (verbatim), `token_type = "teacher"`, an optional `class_id`, and a `description` audit label combining the pipeline name and the mint scope (origin vs. a specific target class), derived from the token's identity rather than the calling step. The OIDC token authenticates the mint; the returned portal token is what the downstream calls use.
- **Token cache (per run).** Mint lazily and cache the returned token for the duration of the run so steps reuse it rather than minting per call, keeping mint calls minimal and staying inside the forwarded Firebase token's ~1-hour life.
- **A map of tokens, not a single token.** A step may act on a class other than the student's origin class (the spring enroll targets the treatment/control `clazz_id`; fall steps target `-Gator`/`-Shark` classes), and a cross-class mint can resolve to a different teacher than the origin class's. The cache is therefore a **map keyed by mint scope and target class** (the origin-class mint is one key; each `class_id` is another), so an origin-class token and one or more target-class tokens coexist within a run and each is reused across the steps that act on that class. The cache lives on the run context (via `StepContext`), created per run and never persisted beyond it.
- Provide a general accessor (for example `getToken({ scope, classId? })`) that returns a cached token or mints on a miss, so this story's spring wiring and the sibling fall stories share one path. Do not re-fetch or re-mint the forwarded Firebase token, and do not refresh a minted portal token; on expiry the run fails per the error rules.

### Cut the existing spring-2026 calls over to the mint flow

- **Enroll** (`random-assignment.ts`): mint a teacher token for the destination `clazz_id` (a **cross-class** mint, `class_id = clazz_id`), and call `add_to_class` with that token. The correct enrolling identity is a teacher **shared between the origin and destination classes**: `add_to_class` authorizes both `update_roster?` on the destination class **and** `student, :show?` on the student, and a shared teacher satisfies both (they teach the destination class for the roster, and the origin class where the student is currently enrolled for the view). This is exactly what the cross-class mint guarantees (it resolves `least_privileged_teacher(origin.teachers & destination.teachers)`); a study with no shared teacher yields a mint `422` that maps to the "tell your teacher" bucket. **This makes a shared teacher a study-configuration precondition, not just an edge case:** each participating student's origin/pre-test class and the study's destination (`-Gator`/`-Shark`) classes must share at least one teacher account, or enroll fails for those students. The spring study is set up this way today; treat it as an operator-verifiable assumption at cutover.
- **Lock** (`lock-activity.ts`): mint the **origin-class** teacher token (default mint, no `class_id`) and call `update_student_metadata` on `resource_link_id` with that token. `lockActivity` must now destructure `firebaseJwt` from its `StepContext` argument (it currently does not).
- **Notify** (`send-email.ts`): switch from `oidc_send` to `send_class_teachers`, authenticated by the **origin-class** teacher token, with body `{ class_id, subject, message }` where `class_id` is the student's origin class. Resolving the origin `class_id` from `resource_link_id` (the notify step has the offering, not the class) is done with a light portal read using the minted token (see Technical Notes); it does not depend on the REPORT-79 class-lookup helper.
- All three downstream calls send `Authorization: Bearer <minted teacher portal JWT>` (the `jwt_bearer_token` path) instead of the OIDC token, against the existing endpoints (enroll/lock) and `send_class_teachers` (notify).
- Thread the mint and token selection through the shared helper (`portal-api.ts`) so the auth wiring lives in one place; `portalOidcFetch` already returns `{ status, data }`, so branching on `status`/`details.reason` needs no change to its return shape.

### Security

- **Validate `platform_id` before forwarding.** The forwarded Firebase token is a bearer credential with no audience binding, sent to `platform_id` (a client-supplied host). `submit-task.ts` whitelists context *keys* but does not validate the `platform_id` *value* (`submit-task.ts:94-107`); `platform_id` is then used verbatim as the `portalUrl` host for **every** portal call in the run (mint, enroll, lock, notify, and the notify offering-read), not just the mint. Validate `platform_id` against a set of trusted portal hosts **once per run, before the first outbound portal request** (i.e. at run setup, before the pipeline loop), so the check structurally gates every portal call rather than only the mint, and introducing the mint call does not create a token-exfiltration surface. **Reuse the host-allowlist pattern report-service already has** rather than inventing a new one (see Technical Notes): parse `platform_id` as a URL, require `https:`, and check the hostname against a trusted-host allowlist. On a validation failure, fail the run at setup before any outbound portal request (no Firebase token forwarded, no mint attempted), log the rejected host only (never a token), and surface the "tell your teacher" message. The allowlist source (a `defineString` config param vs. a hardcoded list) and exactly where the check lives are `implementation.md` details.
- **Never log a token value.** The forwarded Firebase token (the mint input) and the minted portal JWT are both live bearer credentials; neither value may ever be written to logs. Log presence/length and the non-secret fields only (`status`, `details.reason`, the mint `description`), and never echo request headers or credentials when logging a response body. Note specifically that the mint's `201 { token }` **success** body is the one portal response body that contains a live secret (failure bodies carry no token), so the mint response body must never be logged even though the existing enroll/lock/notify call sites log `{ status, data }` on failure; the mint call must not copy that failure-logging pattern onto its success response.
- Send a `description` audit label (pipeline + mint scope, e.g. `spring-2026:origin` / `spring-2026:class-<id>`) on every mint so the portal's mint log and the token's `minted_for` claim tie the token to its pipeline run and class scope. Derive the label from the token's scope, **not** the calling step: a cached token is reused across the steps that act on its class (lock and notify share the origin token), so a step-based label would attribute the second step's calls to whichever step minted first. Scope-based labelling stays accurate for a shared token; per-step tracing remains available in report-service's own structured logs. It is untrusted, log-and-claim input on the portal side (sanitized server-side), so never place a secret in it.

### Error handling

- Classify a failed portal call into coarse, reliably-distinguishable buckets in a single shared helper reused by the mint, the three original call sites (enroll/lock/notify), **and the notify offering-read** (`GET /api/v1/offerings/:resource_link_id`, the fourth portal call introduced by the notify `class_id` resolution); surface a bucket-appropriate student message; and log `status` and (where present) `details.reason`, never the token value:
  - **Mint `422` with `details.reason: "expired"`** is **terminal for this run** (report-service cannot re-mint): a "your session may have expired, please reload the activity and click *I'm Done* again" message (a fresh click re-mints via the Activity Player host).
  - **Any other mint failure** (`422` with a different `reason`, `422` for `token_type`/`class_id` resolution, or a `401`/`403` auth failure) is a config/authorization problem retry cannot fix: a "something went wrong setting up your class, please tell your teacher" message. The `401` arises because the mint's `require_api_user!` runs before `require_token_minter!`, so an unauthenticated caller returns `401` rather than `403`; bucket the two together by HTTP status, and do **not** let a mint `401` fall through to the generic retry bucket.
  - **Downstream `403`** (the acting teacher is not authorized for the class/resource, e.g. `send_class_teachers` `class_teacher?` denial, or an `api_show?` denial on the offering-read) maps to the same "tell your teacher" message. Recall this `403` body is the thin Pundit shape (`{ success: false, message: "Not authorized" }`, no `details`), so the bucket is chosen by HTTP status, not by `details.reason`.
  - **Offering-read failure** (the notify `class_id` resolution): a `404`/`403` here means the origin `class_id` cannot be resolved, so notify cannot proceed; classify by status into the "tell your teacher" bucket (for `403`/`404`) or the generic retry bucket (for `5xx`/network), and never treat an unresolved `class_id` as success.
  - **2xx-non-success / 5xx / network / other (non-4xx)**, including the enroll `2xx`-but-`data.success !== true` case (`random-assignment.ts:407`) and any endpoint-specific success predicate, map to the existing generic "please try again or contact your teacher" message, so a 2xx-non-success is never misread as success. (Any non-`expired` 4xx is a client/config/authorization error and maps to the "tell your teacher" buckets above, never to this generic bucket: the classifier buckets purely by HTTP status, sending all 4xx except mint-`422`-`expired` to tell-your-teacher.) A **thrown** fetch error (network failure) produces no `{ status, data }` response for the classifier to inspect (`portalOidcFetch` does not wrap `fetch` in try/catch, so it propagates), so the call sites must keep catching thrown errors and route them into this generic bucket, exactly as the existing enroll/lock/notify `try/catch` blocks already do.
- Do not add retry/backoff for portal calls, and never re-mint the forwarded token or refresh the minted token. `executeTask` already marks a step failure as a job failure without Cloud Tasks redelivery; that stands. The forwarded Firebase token has a hard ~1-hour life that starts at enqueue, so the pipeline must make its mint and portal calls promptly.

## Rollout sequencing

- Because this story **switches the spring-2026 pipeline** to the mint flow, and the flow **actively calls the mint** (a `403` if the client's `can_mint_scoped_tokens` is off), it is a **cutover with a hard ordering dependency, not an additive no-op**. The required order (already forced by the epic): (1) the portal ships RIGSE-352 and sets `can_mint_scoped_tokens = true` on the report-service OIDC client; (2) report-service deploys this story, at which point spring cuts over to minting. There is **no report-service feature flag** (option A): the portal opt-in is the gate, and a revert is a report-service rollback. (The old spec's "unconditional, no-op-until-opted-in" reasoning does not carry over, since the mint is actively called.)
- **Fail-closed config precondition: `TRUSTED_PORTAL_HOSTS` must be set in the deployed env.** The `platform_id` allowlist gate rejects **every** run at setup when `TRUSTED_PORTAL_HOSTS` is unset or empty (an unset `defineString` resolves to `""`), so the param is a hard deploy precondition alongside the RIGSE-352/client-opt-in ordering: `functions/.env.report-service-pro` -> `learn.concord.org`, `functions/.env.report-service-dev` -> `learn.portal.staging.concord.org` (both committed), and the emulator `functions/.env.local` -> staging + loopback. The `.env.<project>` edits ride in the same commit as the gate. Because rollout is manual with no alerting, a forgotten param would silently break 100% of student runs; watching the mint/portal logs during rollout is the detection.
- **spring-2026 traffic at flip time (confirmed with PI, 2026-07-28).** Trudi (PI) confirmed the spring-2026 study is **no longer in use**: there is no live student "I'm Done" traffic at deploy time. The cutover is therefore low-risk at flip time, and validation relies on a synthetic/staged run rather than live traffic (see the emulator/integration testability note in Technical Notes).
- **Rollout is manual, no alerting/dashboards.** The operator (Doug) runs the deploy and watches the structured mint/portal logs (`status`, `details.reason`, never a token) during rollout; the never-log and structured-logging requirements above are sufficient. This story adds no alerting, dashboards, metrics, or rollout automation, and no rollback runbook beyond "roll report-service back" (the old OIDC-mapped-user path still works while the portal flag stays on).

## Acceptance criteria

- Report-service mints a `teacher`-scoped portal token via `POST /api/v1/jwt/oidc_mint` (OIDC-authed, `firebase_token` = the forwarded custom token, with a `description`), caches it per run in a **map keyed by scope and class**, and reuses it across steps; a step acting on a different class mints and caches a separate token.
- The spring enroll (`add_to_class`) uses a cross-class teacher token for the destination `clazz_id`; lock (`update_student_metadata`) uses the origin-class teacher token; both send `Authorization: Bearer <portal JWT>` against the existing endpoints.
- The spring notify step calls `send_class_teachers` with `{ class_id: origin_class_id, subject, message }` using the origin-class teacher token, and the origin class's teacher(s) receive the email.
- `platform_id` is validated against trusted portal hosts once per run, before the first outbound portal request (so it gates the mint and all downstream calls, including the notify offering-read).
- An **untrusted `platform_id`** fails the run at setup, before any outbound portal request: no Firebase token is forwarded and no mint is attempted; the rejected host is logged (host only, never a token) and the student sees the "tell your teacher" message.
- The shared classifier (covering the mint, enroll, lock, notify, and the notify offering-read) maps mint-`422`-`expired` → reload-and-retry, other mint failures (including a mint `401`/`403` auth failure) / downstream `403` / offering-read `403`/`404` → "tell your teacher", and other/`5xx`/network/enroll-2xx-non-success → generic retry; it chooses the downstream `403` bucket by HTTP status (that body is the thin Pundit shape with no `details`), and logs `status` + `details.reason` and never a token value.
- No token value (forwarded Firebase or minted portal) appears in any log.
- The production spring-2026 pipeline no longer relies on the legacy OIDC-mapped user for any of its three calls.

## Technical Notes

- **Shared helper**: `functions/src/tasks/portal-api.ts`. Add a `mint({ scope, classId?, description })` call to `oidc_mint`, the per-run token cache/map accessor, and a way to make a portal call authed with a minted token (the `jwt_bearer_token` path) vs. the existing OIDC path (still used for the mint call itself). Exact shapes are `implementation.md` decisions.
- **Token cache**: a per-run map keyed by `(token_type, class_id | "origin")`, carried on `StepContext`. This requires **adding a new field to the `StepContext` type** (`ai4vs-flvs/types.ts`), which today has only `jobPath`, `jobDoc`, `firebaseJwt?`, and `stepResults`; the `StepContext` is constructed once per run in `index.ts` (line 53), which is the natural place to initialize the empty map. In spring, lock and notify share the `"origin"` key; enroll uses the destination `class_id` key. All three resolve to the same study teacher in spring but are separate mint calls (report-service cannot see the resolved teacher), which the map deduplicates by class.
- **Notify `class_id` resolution**: `send_class_teachers` requires a `class_id`, but `send-email.ts` has only `resource_link_id`. Resolve the origin `class_id` from the offering with a light portal read (`GET /api/v1/offerings/:resource_link_id` → `clazz_id`) using the minted origin-class teacher token, before the `send_class_teachers` call. This keeps the story self-contained (no dependency on the REPORT-79 class-lookup helper). Alternatively, if RIGSE-352 later returns the origin class in the mint response, the read can be dropped; do not assume it does today. The offering-read authorizes `api_show?` (`class_teacher_or_admin? || class_student? || class_researcher?`), which the origin-class minted teacher satisfies.
- **Notify origin-class invariant**: notify mints the origin-class token (teacher of the class the forwarded token resolves from its `offering_id`, per RIGSE `forwarded_firebase_token.rb`) but sends `send_class_teachers` to the `clazz_id` returned by the offering-read on `resource_link_id`. These agree only when the offering named by the token's `offering_id` and the offering named by `resource_link_id` belong to the same class, which holds because both come from the same LTI launch. If they ever diverged, the acting teacher would not be a teacher of the resolved `class_id` and the call fails into the `403` "tell your teacher" bucket (a safe failure, never a wrong-recipient email). Treat "the `resource_link_id` offering shares the class the token resolves as origin" as an invariant of the launch flow.
- **`platform_id` host-allowlist reuse**: report-service already validates a client-supplied host against an allowlist, so reuse that pattern rather than a new one. `chat/fetch-activity.ts` (`resolveActivityUrl` + `AUTHORING_HOSTS`) parses the value with `new URL()`, requires `https:`, and rejects any hostname not in the allowlist. Note the precedent's allowlist (`AUTHORING_HOSTS`, `fetch-activity.ts:16`) is a **hardcoded const array**, not a config-backed list; the separate `defineString("AUTHORING_HOST")` (singular, `chat-tutor.ts:33`) is a single host for the default-fetch path, not the allowlist. So "reuse the pattern" means the parse/require-https/allowlist shape, and the allowlist *source* (a `defineString` config param vs. a hardcoded list) stays the open `implementation.md` choice noted in Security, not something the precedent already settles. `auto-importer.ts` (`getDomain` / `checkIfDomainsMatch`) additionally shows report-service already extracts and compares the `platform_id` domain specifically.
- **Call sites**: `random-assignment.ts:396` (`add_to_class`), `lock-activity.ts:30` (`update_student_metadata`; add `firebaseJwt` to its destructure), `send-email.ts:65` (`oidc_send` → `send_class_teachers`, body `{ class_id, subject, message }`; also add `firebaseJwt` to its destructure).
- **Preserve each call's existing request encoding.** The cutover swaps only auth (enroll, lock) and endpoint + body (notify); it must not change how each body is encoded. Verified encodings today: enroll posts JSON (`application/json`), lock sends `application/x-www-form-urlencoded` via `URLSearchParams` (`locked=true&user_id=...`), and notify currently posts JSON. Keep enroll and lock byte-compatible with today; for notify, send `{ class_id, subject, message }` as JSON to `send_class_teachers`.
- **Token type**: `StepContext.firebaseJwt` is the portal-minted custom token; forward it verbatim as `firebase_token`. The minted portal JWT is opaque to report-service; send it as `Authorization: Bearer` and never inspect or log it.
- **Error-response shape**: `{ success, response_type: "ERROR", message, details? }`; the mint's forwarded-token failures carry `details.reason`. Only `expired` needs singling out.

#### DISMISSED: Serial `taskWorker` + added mint round-trips could push tokens toward `expired`
Investigated: `taskWorker` runs `maxInstances:1 / maxConcurrentDispatches:1` (serial), and the mint flow raises per-run portal round-trips from 3 to ~6 (origin mint, destination cross-class mint, notify offering-read). Dismissed per project owner: the portal serves these API calls in milliseconds, so the added round-trips do not create a meaningful queue-latency or token-expiry risk (spring is inactive regardless, and fall throughput is REPORT-82's concern).

#### RESOLVED: The reuse-precedent allowlist is a hardcoded const, not a `defineString`-backed list (Senior Engineer / Cross-Repo Contract)
**Resolution**: Applied. Verified `chat/fetch-activity.ts:16` is a plain `export const AUTHORING_HOSTS = [...]` (hardcoded), and the only `defineString("AUTHORING_HOST")` (`chat-tutor.ts:33`) is a *single* host for the default-fetch path, not the allowlist. The Technical Notes `platform_id` bullet previously described the reused allowlist as "a `defineString`-backed list," which could send an implementer looking for a config-driven allowlist that does not exist. The bullet now describes the precedent as a hardcoded const array and keeps the allowlist-*source* choice (config param vs. hardcoded) as the open `implementation.md` decision already noted in Security.
