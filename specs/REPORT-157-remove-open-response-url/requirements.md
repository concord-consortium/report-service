# Remove Open Response URL Columns from the Student Answers Report

**Jira**: https://concord-consortium.atlassian.net/browse/REPORT-157
**Repo**: https://github.com/concord-consortium/report-service
**Implementation Spec**: [implementation.md](implementation.md)
**Status**: **In Development**

## Overview

Add a "Remove open response URL" checkbox to the report server's report generation form. When a researcher checks it, the Student Answers report leaves out the link column that normally follows each open response question, which makes the report much shorter for resources with many open response questions.

## Project Owner Overview

In the Student Answers report, every open response question produces two columns: the student's text answer and a link to the portal report's single-question view, where a teacher or researcher can hear an audio response. Research teams whose modules don't use audio responses get nothing from the link column, and in a long sequence it roughly doubles the number of open response columns. That makes the downloaded CSV hard to scan and work with.

This story adds a checkbox, unchecked by default, to the form researchers already use to create a report. When it is checked, the report's generated query does not produce those link columns, so they never appear in the output. Reports made without the checkbox are unchanged. The ticket also asks that the teacher-facing downloadable CSV drop the column. That is already covered by CLASSDASH-116, the class dashboard's "Download as CSV" in portal-report, which gives each open response a single column with no separate link column, so this story needs no work there.

## Background

The ticket was cloned from CLASSDASH-116 and moved to the REPORT project because it is a report server feature. The requester, a researcher, explains in the comments that each open-ended question produces a text column and a second column holding a link, which they believe points to recorded voice responses. Their modules don't use voice responses, and on sequences with many questions these columns make student answer reports "SUPER LONG". They asked for a checkbox on the reports form that lets researchers remove the column. They also asked that the teacher downloadable CSV leave the column out when it holds no real data. That CSV is specified separately in portal-report (`specs/CLASSDASH-116-add-downloadable-csv/`). It includes no `_url` columns and gives each open response one column holding the student's text. For an audio-only answer, that column instead holds the link to the single-question view, since it is the only way to reach the recording from the file. That spec also notes that the link does not point at the audio recording itself. It opens portal-report's single-question view of the student's answer, where an audio answer can be played.

In the report server (`server/`, Elixir/Phoenix LiveView), the Student Answers report (`slug: "student-answers"`) is an Athena report. Its SQL is generated by `ReportServer.Reports.Athena.SharedQueries.generate_resource_sql/4`. For `report_type == :answers` it calls `get_columns_for_question/5` for each question in each resource. For an `open_response` question, that function returns two columns:

- `res_<n>_<question_id>_text`: the answer text, or empty when the stored answer is the report-state placeholder JSON.
- `res_<n>_<question_id>_url`: a `CONCAT(...)` that builds a portal-report single-question URL (`iframeQuestionId`, class, offering, studentId, `answersSourceKey`). Unlike other question types this URL is unconditional, because a student can answer with audio alone, in which case no text answer exists.

Report options that are not filters already travel through `%ReportFilter{}`. `hide_names` is the model: `ReportFilter.from_form/2` reads it from the form params, the report run persists it through `EctoReportFilter` (a JSON map), the run summary shows it, and `generate_resource_sql/4` pattern-matches it out of the filter. A report opts into showing the checkbox through `form_options` in `ReportServer.Reports.Tree`, e.g. `form_options: [enable_hide_names: true]`, and `ReportLive.Form.get_form_options/2` turns those into assigns the template reads.

The open response `_url` column also has an internal consumer. For `student-answers` runs, the post-processing page offers the `"details"` steps (`JobServer.get_steps("details")`). Two of them, `HasAudio` ("Add has_audio column for open response answers") and `TranscribeAudio`, find the answer through `Helpers.get_answer/2`. That calls `parse_res_answer_col/2`, which reads `res_<n>_<question_id>_url` to get the `answersSourceKey`. Without the column, both steps would fail for every row.

## Requirements

- The Student Answers report's generation form shows a checkbox labeled "Remove open response link columns (audio/report links)". It sits on its own row, in the same stacked checkbox layout as "Hide names": directly below "Hide names" when that checkbox is shown, and directly below the date row when it isn't. Like "Hide names", it appears once the first filter is chosen.
- The checkbox is unchecked by default every time the report's form is opened. The form has no reset control; it starts from empty params on each visit (`handle_params/3`).
- The checkbox appears only on reports that opt in through `form_options`. In this story only Student Answers opts in, because it is the only report that emits per-question columns.
- The checkbox is available to every user who can run the report. It is not role-gated the way Hide names is.
- When the checkbox is checked, the generated Athena SQL contains no `res_<n>_<question_id>_url` column for any `open_response` question, in the header row or in the data rows.
- When the checkbox is checked, every other column is unchanged, including the open response `_text` and `_submitted` columns, and the `_url` columns of `iframe_interactive`, `clue_text_tile`, `clue_question` and `clue_tile` questions.
- When the checkbox is unchecked, the generated SQL is identical to what it is today.
- When the checkbox is checked, no column marks an audio-only open response answer, so it reads like a skipped question: its `_text` cell holds no answer text. That cell is usually empty. When the report-state placeholder is stored JSON-escaped, the cell holds the raw placeholder instead, in checked and unchecked reports alike (REPORT-162). This is an accepted tradeoff: the `_url` column is the report's only sign of an audio answer, and researchers who check the box don't use audio. The `_text` column's content does not change.
- The choice is saved with the report run, so the run's summary shows it as a "Remove Open Response Links: True" row next to "Hide Names", and only when it is on, and duplicating the run keeps it.
- Report runs saved before this change load and behave as if the checkbox was unchecked.
- The report run JSON API accepts the option as an optional boolean in `report_filter` when a run is created. It defaults to `false` when absent and is rejected with the existing "must be true or false" error when it is not a boolean. Every run's returned filter JSON includes it, `false` for older runs.
- The option has the same effect on an API-created run as on a form-created one. `false` is accepted on every report, so a filter copied from any run's JSON can be sent back unchanged. `true` on a report that does not offer the checkbox is rejected with a 400 `BAD_REQUEST` (the API's answer to every `:invalid` filter) and a message such as "This report does not support removing open response links.", the same way `FilterValidation.check_app_supported/2` rejects an application filter. The form path goes through the same validation.
- For a run made with the checkbox checked, the post-processing page does not offer the `HasAudio` or `TranscribeAudio` steps, since they depend on the removed column. The other steps are still offered.

## Technical Notes

- Column generation: `server/lib/report_server/reports/athena/shared_queries.ex`, `get_columns_for_question/5`, the `"open_response"` branch. The option has to reach this function from `generate_resource_sql/4`, which currently destructures only `hide_names` from `%ReportFilter{}`.
- Option storage: `server/lib/report_server/reports/report_filter.ex`. Add a boolean struct field with default `false`, read in `from_form/2` the way `hide_names` is (`form.params[...] == "true"`). `EctoReportFilter.load/1` uses `struct!/2`, so old rows missing the key get the default. `dump/1` writes every struct key, so every run saved after the deploy carries the new key, even when it is `false`. Rolling back to a build without the field would then raise `KeyError` loading those runs, which breaks every runs list that includes one. A throwaway test confirmed both halves of this: a missing key loads as the default, and an unknown key raises. `exclude_internal` and `app` were added under the same constraint, so this story follows precedent. The deploy note should say that a rollback past this release needs the new runs' filters cleaned up, or a forward fix instead.
- Form: `server/lib/report_server_web/live/report_live/form.html.heex`, next to the Hide names checkbox, gated by a new `@form_options` entry computed in `form.ex`'s `get_form_options/2`. The report opts in in `server/lib/report_server/reports/tree.ex`.
- Run summary: `server/lib/report_server_web/components/custom_components.ex`, next to the "Hide Names" row.
- Post-processing: `server/lib/report_server_web/live/report_live/post_processing.ex` maps `student-answers` to `"details"` and calls `JobServer.get_steps/1`. The audio steps depend on `Helpers.parse_res_answer_col/2`.
- JSON API: `server/lib/report_server_web/api/v1/report_json.ex` (`report_filter_json/1`) and `filter_params.ex` (`base/1`) serialize and parse the filter's modifiers. The new option is added to both, following `hide_names` and `exclude_internal` (`boolean/2` in `filter_params.ex`, `!!` in `report_filter_json/1`).
- Validation: `server/lib/report_server/reports/filter_validation.ex`, `validate/2`, which the form's `submit_form`, the API create and duplicate all call. The check that a report offers the option sits alongside `check_app_supported/2`.
- Consumers outside the server: cc-data-cli sends `report_filter` as an opaque map (`internal/api/reports.go`, `internal/mcpserver/types.go`) and reads no `_url` column, so it needs no change to create runs with the option.
- Existing tests: `server/test/report_server/reports/athena/shared_queries_test.exs` covers the column shape of the CLUE types through `get_columns_for_question/5` and is the natural home for the open response cases.
- The legacy JavaScript query-creator Lambda (`query-creator/create-query/steps/aws.js`) holds a parallel copy of the same `open_response` column code for the portal's older report flow. This spec does not change it.

## Out of Scope

- The teacher downloadable CSV. CLASSDASH-116 in portal-report already puts each open response in a single column with no separate link column. The link appears in that column only for audio-only answers.
- Removing the column as a post-processing step. It is removed at query generation, per the product owner's direction.
- The legacy JavaScript query-creator Lambda used by the portal's older researcher report flow, and any matching checkbox in the portal.
- Removing `_url` columns of other question types.
- Detecting automatically whether a resource uses audio and dropping the column without being asked.
- Marking audio-only answers in the `_text` column when the link column is removed. That covers both a placeholder and moving the link into the `_text` cell, as the teacher CSV does.

## Open Questions

### RESOLVED: Judgment call: Should the option hide the audio post-processing steps, or should those steps be made to work without the column?
**Context**: `HasAudio` and `TranscribeAudio` read the open response `_url` column to find the answer's `answersSourceKey`. Without it they fail for every row, and `HasAudio` would quietly report `false`.
**Options considered**:
- A) Don't offer the two audio steps on runs made with the option.
- B) Have the helper fall back to deriving the source key from `res_<n>_resource_url`, the same fallback the SQL uses, so the steps keep working.
- C) Leave them as they are and let them fail.

**Decision**: A. A researcher who removes the audio link column has said they don't use audio, and hiding the steps is simpler than a second source-key derivation that would have to stay in step with the SQL. B would be the better choice only if people want to remove the column and still transcribe audio.

### RESOLVED: Judgment call: Where should the option live?
**Context**: It is a report modifier, not a filter, but `%ReportFilter{}` is already where `hide_names` and `exclude_internal` are persisted, displayed and duplicated.
**Options considered**:
- A) A new boolean field on `%ReportFilter{}`, following `hide_names`.
- B) A new column or embedded options map on `report_runs`.

**Decision**: A. It is saved, duplicated and shown in the run summary for free, and needs no migration. B would be cleaner if report options grow, but that isn't a reason to take it on now.

### RESOLVED: Judgment call: Which reports show the checkbox, and who can see it?
**Context**: Only the `:answers` report type builds per-question columns. Hide names is role-gated through `HideNames.allowed?/1`.
**Options considered**:
- A) Student Answers only, visible to everyone who can run it.
- B) Every Athena report, visible to everyone.
- C) Student Answers only, gated like Hide names.

**Decision**: A. On any other report the checkbox would do nothing. Removing a link column exposes no data, so it doesn't need a role gate.

### RESOLVED: Low confidence: Is the legacy query-creator Lambda really out of scope?
**Context**: The requester wrote "a checkbox to the portal reports". The portal's older researcher report flow calls the JavaScript query-creator Lambda, which has its own copy of the open response `_url` column code (`query-creator/create-query/steps/aws.js`). If researchers still build Student Answers reports that way, changing only the report server won't help them.
**Options considered**:
- A) Report server form only. Researchers who want the option use the report server.
- B) Also add a query parameter to the Lambda. That needs a matching change in the portal (rigse) to add the checkbox there, so it would be a separate story.

**Decision**: A. Only the report server form gets the option. Researchers who want shorter reports use the report server's Student Answers report. The Lambda is left unchanged.

### RESOLVED: Low confidence: What exactly should the checkbox say?
**Context**: The direction was "something like 'Remove open response url'". Researchers see the column as "the second column" or "the link column". The label sits next to "Hide names", which is short.
**Options considered**:
- A) "Remove open response URL"
- B) "Remove open response URL columns"
- C) "Remove open response link columns (audio/report links)"

**Decision**: C. It tells researchers what they give up. The form stacks each checkbox on its own full-width row ("Hide names" sits alone below the date inputs), so a longer label fits.

### RESOLVED: Should the report run JSON API accept and return the option?
**Context**: `POST /api/v1/...` report runs (REPORT-93) parse `hide_names` and `exclude_internal` in `FilterParams.base/1` and return them in `ReportJson.report_filter_json/1`. cc-data and other API callers create Student Answers runs this way. If the API doesn't parse the option, API-created runs always include the column, and a run created in the UI with the option on won't show it in its API JSON.
**Options considered**:
- A) Yes: parse it as an optional boolean (default `false`) and include it in the returned filter JSON.
- B) Return it in the JSON (so API readers can see how a run was made) but don't accept it on create.
- C) Leave the API alone for now.

**Decision**: A. The API accepts the option as an optional boolean, default `false`, and returns it in every run's filter JSON. That way API-created runs can use it, and API readers can see how any run was made.

### RESOLVED: Should the teacher downloadable CSV be split into a follow-up ticket?
**Context**: The ticket's second request, dropping the column from the teacher CSV when it has no data, belongs in portal-report. Leaving it only as a line in this spec risks it getting lost when the ticket is closed.
**Options considered**:
- A) Create a follow-up ticket in the portal-report project and link it from REPORT-157.
- B) Note it here as out of scope and let the requester decide whether to file it.

**Decision**: Neither. It isn't needed, because CLASSDASH-116 already specifies the teacher CSV with one column per open response and no `_url` columns. The link moves into the answer column only for audio-only answers.

### RESOLVED: How should audio-only answers look once the link column is removed?
**Context**: For an audio-only answer the `_text` cell holds no answer text (it is usually empty; see REPORT-162 for the exception), which is why the `_url` link is always generated for open responses. With the option on, an audio-only answer looks the same as a skipped question. The teacher CSV (CLASSDASH-116) puts the single-question link in the answer's own column instead, for audio-only answers only.
**Options considered**:
- A) Accept it and write down the tradeoff.
- B) Mark audio-only answers in the `_text` cell when the option is on, with a placeholder or with the link as the teacher CSV does. Either needs SQL to detect an audio answer from the stored data, which isn't confirmed to be possible, and moving the link in would bring back the link the researcher asked to remove.

**Decision**: A. Only researchers who don't use audio check the box, and the label names the audio links it removes. The tradeoff is stated in Requirements.

## Self-Review

Stage 3 review of the requirements (Senior Engineer, QA Engineer, Education Researcher, Product Manager, WCAG Accessibility Expert). Each finding below was checked against the code before being recorded. Findings that didn't survive the check were dropped.

### Senior Engineer

#### RESOLVED: The API accepted the option on reports that ignore it
The draft had the API accept `true` on any report, where it would change nothing. That conflicts with `FilterValidation.check_app_supported/2`, which rejects an application filter on a report that doesn't offer one. It would also put a "Remove Open Response Links: True" row in the summary of, say, a Student Actions run that has no such columns. **Fix**: `false` is accepted everywhere, and `true` is rejected with a 400 on reports that don't offer the checkbox.

#### RESOLVED: Rollback breaks loading runs saved after the deploy
`EctoReportFilter.dump/1` writes every struct key, and `load/1` uses `struct!/2`. A throwaway test confirmed that `load/1` raises `KeyError` on an unknown key. So a build without the field can't load any run saved after the deploy. **Fix**: recorded in Technical Notes as a deploy caveat. It follows the precedent of `exclude_internal` and `app`, so the storage approach doesn't change.

### QA Engineer

#### RESOLVED: "After a form reset" isn't testable
The report form has no reset control. `handle_params/3` builds the form from empty params on each visit. **Fix**: the requirement now says the checkbox is unchecked every time the form is opened.

### Stage 4 verification

- **Throwaway prototype of the column change.** Filtering the open response `_url` out of `get_columns_for_question/6` behind an option left the SQL for an unchecked run byte-identical to the current code's (`cmp`). With the option on, the open response `_url` alias disappeared from all three UNION ALL parts. The `iframe_interactive` `_url` stayed, and each part still has the same 15 `res_1_*` aliases in the same order, so the union stays aligned.
- **The API's rejection status.** `ReportController.render_create_error/2` maps every `{:error, :invalid, _}` to `ErrorHelpers.bad_request/2`, so the rejection is a 400 `BAD_REQUEST`. The draft said 422, which was wrong, and has been corrected.
- **Creating a run from the form in tests.** A Student Answers run submitted through the form only inserts the row (`create_run/2`), and the partition count runs only on reports with the application filter. So the form test needs no Athena stub.

### Verified without a finding

- **The column is removed from every row.** A throwaway test generated the full answers SQL for an open response question. `res_1_<id>_url` appears three times: in the Prompt row, the correct-answer row and the data row, all built from the one column list. So leaving the column out of `get_columns_for_question/5` removes it from the header, both label rows and the data.
- **Duplicating keeps the option.** `Reports.duplicate_api_report_run/3` copies the source run's whole `report_filter`.
- **Post-processing uses one step list.** The submit handler uses the same `@steps` assign that `init/2` builds, so filtering the audio steps in one place covers both what's offered and what can be submitted. `GlossaryData` and `MergeToPrimaryUser` don't read `_url` columns.
- **The checkbox label is wired correctly.** The new checkbox follows "Hide names": `<.input type="checkbox" id=...>` plus a `<label for=...>`, so clicking the label toggles it and screen readers announce the label.
- **cc-data needs no change.** It passes `report_filter` through as an opaque map and reads no `_url` column.
