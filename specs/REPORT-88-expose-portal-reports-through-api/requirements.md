# Expose Portal reports through the report-service API

**Jira**: https://concord-consortium.atlassian.net/browse/REPORT-88
**Repo**: https://github.com/concord-consortium/report-service
**Implementation Spec**: [implementation.md](implementation.md)
**Status**: **In Development**

## Overview

<!-- Rewritten during Finalization. -->
Make the Portal report family reachable through the `/api/v1` surface the same way Athena reports already are, so API clients (cc-data and others) can list Portal runs and download their results programmatically instead of only viewing them in the report-server web UI.

## Project Owner Overview

<!-- Rewritten during Finalization. -->
Today the report-service v1 API only knows about Athena-backed report runs. Portal reports (which run live SQL against the portal database and build a CSV in-process) are invisible to every downstream tool, so researchers can only see them in the web UI. This story is the server-side enabler for the rest of the Portal-report work: the new learners report, the cc-data CLI integration, and the skill/guidance updates. After this story, a client can list Portal runs alongside Athena runs, download a Portal run's CSV, and pass a Portal run to the bulk answers/history/attachments endpoints.

## Background

The v1 API is Athena-only today. Both API read paths funnel through two functions in `reports.ex`:

- `list_api_report_runs` (`reports.ex:71`) powers `GET /api/v1/reports` (index).
- `get_api_report_run` (`reports.ex:91`) powers `GET /api/v1/reports/:id` (show), `/download`, `/answers`, `/history`, `POST /reports/:id/attachments`, and the two Athena post-processing job endpoints `GET /reports/:id/jobs` and `GET /reports/:id/jobs/:job_id/download` (`report_job_controller.ex:13,31`). All seven admit a run once its slug passes the gate, so widening the gate changes the job endpoints too; their intended Portal behavior is pinned under Listing and Regression below.

Both gate on `r.report_slug in ^Tree.athena_report_slugs()` (`reports.ex:74,95`), where `Tree.athena_report_slugs()` collects every report in the tree whose module `type == :athena` (`tree.ex:68-73`). Any run whose slug is not an Athena slug is treated as non-existent (`{:error, :not_found}`). This is the single choke point that hides Portal runs.

**Athena vs. Portal run shape.** An Athena run carries `athena_query_id`, `athena_query_state`, and (on success) an `athena_result_url` pointing at an S3 object; download returns a presigned-URL envelope (`{download_url, filename, expires_in_seconds}`). A Portal run has none of that: it has no stored result artifact at all. A Portal report is a `ReportQuery` (SQL) built by the report module's `get_query/2`, run live against the portal DB via `PortalDbs.query/4`, with the CSV built in-process (the LiveView's `format_results(%MyXQL.Result{}, "csv")`, `show.ex:208`). Because a live portal-DB query can be slow, the LiveView offloads it to a supervised async task (`download_portal_report`, `show.ex:245`; `Task.Supervisor.async_nolink` with `:DOWN`/timeout handling), which pushes the result over the LiveView websocket. That websocket mechanism is **not** reusable by an HTTP API controller.

**Portal reports are uniform.** Every Portal report has the same shape (`get_query` -> `ReportQuery` -> SQL -> CSV). The current non-`tbd` Portal reports are `teacher-status`, `resource-metrics-summary`, `resource-metrics-details`, `school-metrics` (Detailed Metrics by School), and `summary-metrics-by-subject-area` (`tree.ex:127-201`). New Portal reports (Student ID Mapping / Student Metadata) will be added later; a type-based mechanism covers them automatically the moment they land. The `tbd: true` flag (`report.ex:5,18`) marks placeholder reports (e.g. `tbd_report.ex`) that must be excluded.

**Bulk derivation is already type-agnostic.** `EndpointSet.derive_endpoint_set` (`endpoint_set.ex:13-36`) derives the per-learner endpoint set from `report_run.report_filter` via `LearnerData.fetch`; it never inspects Athena query state or results. Loosening the `get_api_report_run` gate admits Portal runs to the bulk endpoints; on top of that, a small per-report `derives_learner_data` capability check (not Portal-specific) is added to the shared derivation so aggregate-only reports are rejected cleanly instead of over-pulling (see Bulk endpoints). Note the routes differ: answers and history are `GET`, but attachments is `POST /api/v1/reports/:id/attachments` (a presign-for-download, `router.ex:66-68`).

**The `ensure_current` hazard.** `report_controller.ex` calls `AthenaRunOps.ensure_current(report_run)` in both `show` (`:25`) and `download` (`:37`). `ensure_current`'s first clause matches `%ReportRun{athena_query_id: nil, athena_query_state: nil}` (`athena_run_ops.ex:52`), which is exactly the shape of a Portal run, and it will try to claim the run as `"queued"` and self-start an Athena query. Once the gate opens, Portal runs must be prevented from entering this Athena-only path.

## Requirements

### Listing

- `GET /api/v1/reports` (index) returns Portal runs alongside Athena runs, covering all non-`tbd` `type: :portal` reports. `tbd: true` placeholder reports are excluded.
- `GET /api/v1/reports/:id` (show) returns a single Portal run the caller owns; a Portal run's id is no longer indistinguishable from not-found.
- Each run's JSON gains an `execution` field: `"async"` for Athena runs, `"sync"` for Portal runs, sourced from the report module `type`. Clients branch on this field to choose their download path.
- The existing `report_type` field (`= api_report_type`) is unchanged. Portal runs carry `report_type: null`, which is correct (Portal reports do not declare an `api_report_type`). `report_type` is therefore documented as nullable in the run-JSON contract; clients must treat a null value as expected, not an error.
- A Portal run's Athena-specific JSON fields (`athena_query_state`, etc.) reflect its real (empty/`null`) values and must not trigger any Athena computation on show.

### Job endpoints (Athena post-processing)

- `GET /api/v1/reports/:id/jobs` and `GET /api/v1/reports/:id/jobs/:job_id/download` route through the same shared `get_api_report_run` gate (`report_job_controller.ex:13,31`), so widening the gate admits Portal runs to them as well. Post-processing jobs are an Athena-only concept keyed entirely on `athena_query_id`, and a Portal run has none, so the Portal contract is: `GET /reports/:id/jobs` returns an empty jobs list (`200` with `items: []`), and `GET /reports/:id/jobs/:job_id/download` returns `404`. This is a deliberate contract (a Portal run legitimately has zero jobs), not an accident of implementation, and it is regression-tested (see Regression). No Portal-specific code is required to produce it: `JobsFile.list_jobs(nil) -> {:ok, []}` (`jobs_file.ex:6`) and `find_job(nil, _) -> {:error, :not_found}` already yield exactly this, so the endpoints are left unchanged and the tests lock the behavior in.

### Download

- `GET /api/v1/reports/:id/download` for a non-`tbd` Portal run runs the report's query against the portal DB on request and streams the resulting CSV directly to the client as a chunked response (compute-on-request). There is no presigned-URL envelope, because there is no S3 object to presign. Server memory stays bounded by streaming query batches (`MyXQL.stream`) through the CSV encoder rather than materializing the whole result.
- The Athena download path (presigned envelope, `{download_url, filename, expires_in_seconds}`) is unchanged. The endpoint branches on the report module `type`.
- The download filename follows the existing convention: `#{report_slug}-run-#{id}.csv`. The Portal response sets `Content-Type: text/csv` and `Content-Disposition: attachment; filename="#{report_slug}-run-#{id}.csv"`.
- The streamed CSV is byte-compatible with the web CSV under the report's **default row order** (same column headers, column ordering, delimiter, and quoting), for any result including the empty (zero-row) case, because this story also corrects the web encoder's zero-row output to a header-only line so the two surfaces agree (see the zero-row bullet). One deliberate exclusion from byte-equality remains, documented below: rows re-ordered by an interactive web column sort. Byte-compatibility is scoped to the default order deliberately: the web UI's ad-hoc column sort (`handle_event("sort_column")`, `show.ex:59-72`) lives only in the LiveView session assign (`show.ex:18`) and is threaded into that download (`download_portal_report`, `show.ex:245` -> `add_sort_columns`, `show.ex:196`), but it is never persisted on the `%ReportRun{}` (`report_run.ex:9-19` has no sort field). The API rebuild takes only the run `id` and can only ever emit the report's default `order_by`, so a web CSV downloaded after an interactive column sort is intentionally outside the API CSV contract (rows may be re-ordered; row set and encoding are identical). The exact encoding recipe that yields this byte-equality for non-empty results was verified empirically against a live MySQL 8.0 and is pinned in Technical Notes (Portal-download execution) and Self-Review Round 6.
- The `/download` endpoint is polymorphic: an `application/json` presigned envelope for Athena runs, a chunked `text/csv` body for Portal runs. A client determines which to expect by branching on the run's `execution` field (from list/show), corroborated by the response `Content-Type`.
- A Portal query that matches zero rows returns a header-only CSV with `200` (a single header line derived from the query result metadata, no data rows), not an error. Empty is a valid result, distinct from a failure. A header-only file is unambiguously "a valid empty result," whereas a zero-byte file is indistinguishable from a failed/truncated transfer (which per the streaming contract the client must already guard against), so header-only is the intended empty-result body. The current web `format_results/2` (`CSV.encode(headers: ...)` over an empty row enumerable) emits an *empty* body (zero bytes) for a zero-row result; **this was confirmed empirically in Round 6 to be a pre-existing bug, and this story corrects the web encoder to emit the same header-only line** (project-owner decision, Round 7), so the API and web agree in the empty case rather than diverging. The header row is producible from `MyXQL.stream`'s leading zero-row envelope, which carries the `columns` metadata (verified in Round 6, re-confirmed against live MySQL in Round 7).
- A failure before any bytes are sent returns a clean JSON error. "Before any bytes are sent" covers both failure modes that can occur pre-stream: a failure while *building* the query (`get_query`/`ReportQuery.update_query` returning `{:error, _}`, e.g. the `"Cannot run query with no filters"` short-circuit a super-admin blank-filter run reaches at `report_query.ex:43-44` before any SQL runs) and a failure while *executing* the streamed query (a DB/query error on the first fetch). Both map to the same clean JSON error; neither may fall through as an unhandled `WithClauseError` (which would raise an out-of-contract `500`). A failure mid-stream aborts the chunked response without a clean termination, so the client can detect truncation (an incomplete chunked stream) rather than mistaking a partial file for a complete one. The "no partial file" guarantee is completed at the client: the client stages the body and promotes it to the final filename only on clean stream completion (see the cc-data dependency in Out of Scope). Error responses are generic (the failure is logged server-side); the raw portal-DB error message (`MyXQL`/`DBConnection`) is never included in the API response body, to avoid leaking SQL/schema detail.
- The Portal download is bounded by an API-specific, configurable wall-clock timeout (env var, e.g. `PORTAL_DOWNLOAD_TIMEOUT_MS`, conservative default) rather than the portal DB's 5-minute `@query_timeout`, so a slow query or slow client cannot hold a portal-DB connection/read view indefinitely. Exceeding the timeout returns a clean JSON error if no bytes were sent, or aborts the stream (client-detected truncation) if it was already in progress.
- Concurrent Portal downloads are capped (configurable, small, e.g. 2 per node) so that streaming downloads cannot consume the whole shared portal-DB connection pool. The pool (`portal_dbs.ex`, `pool_size: 5` per server) is shared with authentication (`get_user_info`), authorization (`get_allowed_project_ids`), bulk derivation, and the web UI; a streaming download holds one connection for the whole transfer (up to `PORTAL_DOWNLOAD_TIMEOUT_MS`), so without a cap a handful of concurrent downloads could starve logins and authorization on that portal server. When the cap is reached, an additional download request returns a clean, retryable `503 SERVICE_UNAVAILABLE` before checking out a connection, rather than queuing on the pool. (503 is retryable, unlike `SERVER_ERROR`/500; it is added to `ErrorHelpers` alongside the new 422, a one-line `@statuses`/`@codes_by_status` change.) This is distinct from (and does not depend on) resizing the pool. Note the cap is per node: each Fargate task has its own portal pool of 5 and its own cap, so aggregate concurrent Portal downloads across the deployment are `cap × task_count` (e.g. transiently doubled during a `maximumPercent: 200` rollout), not a single global limit. Per-node is the correct scope for protecting each node's own pool.
- The Portal download has audit parity with the Athena path: the download is recorded in `data_access_log` before any bytes are sent, fail-closed (an audit-write failure returns a clean error and no download). The row uses `source: "api"`, `data_type: "run_csv"`, and a new `event` value (e.g. `"run_csv_streamed"`) that keeps streamed Portal exports distinguishable from presigned Athena downloads in the audit trail. The row records that a download was authorized and initiated (written before streaming, matching Athena's issue-time semantics), not that the full CSV was delivered.

### Bulk endpoints

- `GET /api/v1/reports/:id/answers`, `GET /api/v1/reports/:id/history`, and `POST /api/v1/reports/:id/attachments` accept a Portal run and return that run's learners' data, with the learner set derived from the run's `report_filter` (the primary use case is the forthcoming Student ID Mapping run).
- A report declares whether its runs can produce a per-learner set via a new `derives_learner_data` flag on the `Report` struct (default `true`). Aggregate-only reports, whose output is grouped counts and whose filter vocabulary never narrows to learners, are marked `derives_learner_data: false`. Today that is exactly the two aggregate reports, `school-metrics` and `summary-metrics-by-subject-area` (`include_filters: [:country, :state, :subject_area]`, none of which is one of the seven learner-narrowing dimensions `cohort/school/teacher/assignment/class/student/permission_form`); every other current report (Athena and Portal) declares at least one learner-narrowing filter and keeps the default `true`.
- The three bulk endpoints return a clean `422 UNPROCESSABLE` for a run whose report is `derives_learner_data: false`, replacing today's over-broad project-wide pull (researcher) or `500` (super-admin). This is a per-report capability check keyed on the report module (resolved from the run's `report_slug`), not a per-run filter-shape check and not a hardcoded slug allowlist, so it stays consistent with the ticket's "type-based, no allowlist" principle while giving a single honest response for reports that structurally cannot answer a per-learner request.
- **The `derives_learner_data` flag narrows only the three bulk learner endpoints. It has no effect on the gate, listing, show, or `/download`.** An aggregate report stays fully listable, fetchable, and downloadable through the API (you can download the `school-metrics` CSV; you just cannot request its per-learner answers/history/attachments). The gate (`Tree.api_report_slugs()`) remains `type in [:athena, :portal] and not tbd`, independent of `derives_learner_data`, so a `false` flag never filters a report out of the API surface, it only declines the learner-derivation endpoints.

### Regression

- Existing Athena-specific API behavior is unchanged and regression-tested: `report_type` values, the presigned-envelope download contract, the 409 not-ready/state responses, and index pagination/ordering.
- The two Athena post-processing job endpoints change observably for Portal runs because they share the widened gate: `GET /reports/:id/jobs` for a Portal run flips from `404` (gate-rejected today) to `200` with an empty `items` list, and `GET /reports/:id/jobs/:job_id/download` stays `404` (now "job not found" rather than "run not found"). Athena runs are entirely unchanged on both endpoints. This is a deliberate contract (Portal runs have no post-processing jobs) and must be regression-tested so a future `JobsFile` change cannot silently turn the Portal `/jobs` empty-list into a `500`. Separately, three existing tests encode the *old* Athena-only exclusion of Portal runs and must be updated to the new behavior (not held unchanged): the index "returns only Athena-type runs" assertion (`report_controller_test.exs:52-65`) now expects a Portal run to appear, and the show/download `404` buckets (`:233-253`, `:466-486`) no longer include a Portal run id (it now resolves).
- For bulk, the behavior change is confined to the aggregate reports: a run of a `derives_learner_data: false` report (today `school-metrics`, `summary-metrics-by-subject-area`) newly returns `422 UNPROCESSABLE` on the three bulk endpoints, replacing today's over-broad project-wide pull (researcher) or `500` (super-admin). Every other report is unchanged: a learner-derivable run (Athena or Portal) still derives exactly as today, because those reports keep `derives_learner_data: true` and the `LearnerData.fetch` derivation path itself is untouched.
- Because the check is per-report (keyed on the report module), not per-run (keyed on filter shape), the test change is narrow: the existing `bulk_export_controller_test.exs` and `attachment_controller_test.exs` fixtures use learner-derivable reports (e.g. `teacher-actions`), so they keep the default `derives_learner_data: true` and stay green as seeded, blank filters and all. The new coverage is additive: tests that exercise an aggregate report (`school-metrics`) assert the `422` on each bulk endpoint, and a learner-derivable Portal run asserts normal derivation. This is the regression-cost payoff of choosing the per-report flag over a per-run filter-shape precondition.

## Technical Notes

- **Gate widening.** Replace the `report_slug in ^Tree.athena_report_slugs()` gate in `list_api_report_runs` (`reports.ex:74`) and `get_api_report_run` (`reports.ex:95`) with a gate that admits every non-`tbd` API-exposed slug (Athena plus Portal). Likely a new `Tree` helper (e.g. `Tree.api_report_slugs()`) that collects non-`tbd` reports of `type in [:athena, :portal]`; Athena reports are never `tbd`, so today this is athena-slugs plus non-`tbd` portal slugs. Two stale docstrings live on the exact functions being changed and must be updated in the same commit (same category as the `report_json.ex:56-57` comment above): `reports.ex:68-70` describes `list_api_report_runs` as listing "the caller's Athena-type report runs," and `reports.ex:87-90` describes `get_api_report_run` as getting "the caller's Athena-type report runs" and states "Not-owned and non-Athena ids are indistinguishable from non-existent," which is precisely the not-found semantics the Listing requirement changes for Portal runs. Guardrail on the helper itself: `collect_reports/1` (`tree.ex:75-76`) recurses into `%ReportGroup{children: ...}` *unconditionally* and never consults a group's own `tbd` field (group-level `tbd`, e.g. the commented-out `codap-reports` group at `tree.ex:202-203`, is only a decorative 🚧 badge in the web UI). So the new `api_report_slugs` helper must honor `tbd` across the full parent chain (not just leaf `Report.tbd`), otherwise a future WIP `%ReportGroup{tbd: true}` whose children are ordinary non-`tbd` `Report` structs would be silently exposed through the API while the web UI still badges it as under construction. No currently-live report is affected (all five Portal reports are individually non-`tbd`).
- **`execution` source.** Resolve the run's report module via `Tree.find_report(report_run.report_slug)` and map `type: :athena -> "async"`, `type: :portal -> "sync"` in `report_json.ex` `run_json/1`. `report_json.ex` already resolves the module for `report_type` (`report_json.ex:58-63`), so this reuses the same lookup. (Implementation note: `report_json.ex:56-57` currently comments that the `nil` `report_type` fallback is unreachable because the API is Athena-only; update that comment when the gate widens, since the fallback becomes the intended `report_type: null` path for Portal runs.)
- **`ensure_current` guard.** Guard the `AthenaRunOps.ensure_current` calls at `report_controller.ex:25,37` so Portal runs skip Athena state machinery. Branch on the resolved report `type` (via `Tree.find_report(report_run.report_slug)`) so only Athena runs call `ensure_current`. A `type: :portal` guard clause directly on `ensure_current` is not an option: it receives a `%ReportRun{}`, which has no `type` field (`report_run.ex:9-19`); `type` lives on the `Report` module and must be resolved from the slug first.
- **Portal download execution.** Build the query the same way the LiveView does: `report.get_query.(report_run.report_filter, report_run.user)` -> `ReportQuery.get_sql/1,2` (`get_api_report_run` preloads `:user`, so `report_run.user.portal_server` is available). Both build steps can fail before any SQL is streamed and must be mapped to the clean pre-stream JSON error (per the Download requirement), not left to raise: `get_query`'s tail `ReportQuery.update_query/2` returns `{:error, "Cannot run query with no filters"}` for an all-empty `join`/`where` (`report_query.ex:43-44`), which a super-admin (`:all`, so `apply_allowed_project_ids_filter` adds nothing) reaches on a blank-filter run, and `get_sql` returns `{:ok, sql}` but should still be matched rather than assumed. Only open the stream (`send_chunked`) once both `{:ok, _}` are in hand; a `{:error, msg}` from either step returns the pre-stream JSON error. This `"Cannot run query with no filters"` string is an app-level constant (not a raw `MyXQL`/`DBConnection` message), so it is exempt from the SEC2 leak concern and may be surfaced or genericized. Then, instead of `PortalDbs.query` (which materializes the whole `%MyXQL.Result{}`), run the SQL through `MyXQL.stream` inside a checked-out connection so rows arrive in `max_rows` batches, encode each batch with `CSV.encode`, and write each encoded chunk to the connection via `Plug.Conn.send_chunked/2` + `chunk/2`. Only the *encoding rules* are shared with the LiveView (column-header derivation, row mapping, and the existing `CSV.encode` options, note the LiveView's `delimiter: "\n"`); the LiveView materializes and encodes once (`format_results/2`, `show.ex:208-216`) while the API encodes per batch, so factor out the encoding rules (not the whole function) and require the API CSV to be byte-compatible with the web CSV (same headers, ordering, delimiter, quoting). Streaming detail (all envelope behavior below **empirically confirmed in Round 6** against a live MySQL 8.0, not only from the myxql docs): `MyXQL.stream` yields a leading `num_rows: 0` result carrying the `columns`, and a trailing `num_rows: 0` result when the total row count is divisible by `max_rows` (`myxql.ex:723-745`); a zero-row query yields *two* zero-row envelopes (leading + trailing), both carrying `columns`. The header row must be emitted exactly once from the first result's `columns`, the zero-row envelope results (leading and any trailing) must be skipped, and only non-empty row batches encoded, so the streamed CSV is byte-identical to the web CSV rather than repeating the header per batch. **The exact byte-compatible recipe, verified byte-identical to `format_results/2` in Round 6:** emit the header as one CSV-encoded row of the column-name strings, then encode each non-empty batch's rows as **list-of-lists** (the raw `MyXQL` row lists, already in column order, *not* remapped to maps), all with `delimiter: "\n"`. The naive alternative, `CSV.encode(headers: ...)` per batch, was confirmed to repeat the header mid-file and is wrong (SE4). **Empty-result handling:** for a zero-row query the API emits a header-only line (from the leading envelope's `columns`); this story also corrects the web encoder to emit the same header-only line for a zero-row result (previously an empty body, a pre-existing bug), so the empty case is byte-equal across the two surfaces rather than an exclusion (see the Download zero-row requirement and R6-1). This needs a new streaming entry point on `PortalDbs` (a `stream`/`run` wrapper) since it exposes only `query/4` today; make it swappable via `Application.get_env` (like `athena_db`/`learner_data`/`allowed_project_ids_source`) so the streaming-download and timeout paths are testable without a live portal DB.
- **Portal-DB timeout.** `PortalDbs` uses `@query_timeout 300_000` (5 min, `portal_dbs.ex:9`). Streaming to the client holds a portal-DB connection (and read view) for the whole transfer, so the download is bounded by an API-specific, configurable wall-clock deadline (env var, e.g. `PORTAL_DOWNLOAD_TIMEOUT_MS`, conservative default ~120_000 ms). Because `MyXQL.stream`'s `:timeout` only bounds each per-batch fetch, the overall deadline must be tracked explicitly in the chunk-writing loop (plus a per-batch fetch timeout on the streamed query). Pool sizing (increasing `pool_size`) is intentionally out of scope, but shared-pool contention is addressed by the concurrent-download cap (see the Download requirements): the per-server pool (`pool_size: 5`) is shared with authentication, authorization, bulk derivation, and the web UI, so downloads must be capped below the pool size to guarantee connections remain available for auth/authz. Accepted risk (separate, and remaining after the cap): streaming holds a portal-DB connection and (via `MyXQL.stream`) potentially an open read view on the *production* portal DB for the download duration, a DB-health concern (undo-log/read-view pressure) distinct from pool sizing. It is bounded by the timeout above. Note the open read view is inherent to `MyXQL.stream` (which must run inside a transaction), so it cannot be avoided by choosing a lighter checkout; the timeout and the concurrent-download cap are what bound it.
- **Audit.** `AuditLog.issue_download_url` (`audit_log.ex:17`) is presign-shaped and writes a `download_url_issued` row; a Portal download issues no URL. Add a sibling fail-closed function modeled on `log_attachment_urls/3` (`audit_log.ex:56`) that writes one `DataAccessLogEntry` with `source: "api"`, `data_type: "run_csv"`, and a new `event: "run_csv_streamed"` (add the value to the `validate_inclusion` list in `data_access_log_entry.ex`, no migration). Call it before `send_chunked`; gate the stream on `{:ok, _}` and return `SERVER_ERROR` on `{:error, _}`. The audit UI needs no change (renders the event verbatim).
- **Bulk endpoints.** The gate change (shared `get_api_report_run`) is enough to admit Portal runs; `EndpointSet.derive_endpoint_set` is already type-agnostic (`endpoint_set.ex:29-34`). Add: (1) an `UNPROCESSABLE`/422 code in `ErrorHelpers` (`@statuses` / `@codes_by_status`, currently 400/401/404/409/410/500) plus, in the same one-line change, a `SERVICE_UNAVAILABLE`/503 code used by the Portal-download concurrency cap (see Download requirements); (2) a `derives_learner_data: true` field on the `Report` defstruct (`report.ex:5`), set `false` on the two aggregate `%Report{}` literals in `tree.ex` (`school-metrics`, `summary-metrics-by-subject-area`); and (3) a per-report capability check inside `EndpointSet.derive_endpoint_set` that resolves the run's report via `Tree.find_report(report_run.report_slug)` (the same lookup the `execution` field and the `ensure_current` guard use) and short-circuits to a `422` sentinel when `derives_learner_data` is `false`, before calling `LearnerData.fetch`. Implement it as a small multi-headed function, e.g. `ensure_bulk_derivable(%Report{derives_learner_data: false}) -> {:error, :not_learner_derivable}` and `ensure_bulk_derivable(%Report{}) -> :ok`. It goes **inside `derive_endpoint_set`**, the single shared path (`/attachments` at `attachment_controller.ex:17` and `/answers`,`/history` all route through it), so one placement covers all three endpoints. Its `422` sentinel must be mapped **before** the existing generic `{:error, _} -> ErrorHelpers.server_error(conn)` clauses in both controllers (`bulk_export_controller.ex:77`, `attachment_controller.ex:41`), which are matched top-to-bottom; a clause after them is dead code and these runs would keep returning `500`. This replaces the current `server_error` mapping (`bulk_export_controller.ex:77`) for the super-admin case and heads off the over-broad researcher pull (today the successful `{:ok, endpoints}` branch at `:53`). Genuine derivation failures on a derivable report still map to `server_error`. The flag is read only here, so listing/show/download stay unaffected.
- **Bulk-derivability consistency test.** `derives_learner_data` is a hand-set flag with a `true` default, so a future aggregate report could be added without it and silently fall back to the old over-broad/`500` behavior instead of a clean `422`. ## Open Questions

### RESOLVED (Q1): What is the download streaming/timeout strategy, and what does a client see on a slow/failed query?
**Context**: The ticket explicitly says to decide this rather than assume the LiveView's async handling is reusable. A Portal query can take up to the 5-minute `@query_timeout`. The acceptance criterion is "a slow/failed query returns a clean error, not a hang or partial file." The choice affects the observable error contract, so it belongs in requirements, not just implementation.

Verified during the decision:
- `MyXQL.query/4` (what `PortalDbs.query` calls) returns a fully-materialized `%MyXQL.Result{}`. True row-by-row streaming requires `MyXQL.stream/4`, which yields `max_rows`-sized batches (default 500) from a checked-out `%DBConnection{}` (`myxql.ex:751`).
- The LiveView's `format_results/2` (`show.ex:208`) already builds the entire CSV string in memory (`Enum.to_list |> Enum.join`), so the existing web path is fully-materialized on the same box.
- Production (CloudFormation stack `report-server-prod`; infra lives in the AWS console, not the repo, per `server/README.md:109-114`) is understood to run on small Fargate tasks (assumed ~`ContainerMemory: 2048`/2 GB, `ContainerCpu: 1024`; these values are console-only and unverified from the repo). Nominally `DesiredCount: 1`, though the deploy runs `maximumPercent: 200`, so two tasks exist transiently during a rollout. Either way each task has its own ~2 GB and its own per-server portal pool of 5, so bounding per-task memory is what matters. All current Portal reports are `GROUP BY` aggregations (bounded row counts), but the future Student ID Mapping report is plausibly row-per-student and large.
- Plug's `send_chunked/2` + `chunk/2` are available (`plug/conn.ex:515,553`). No endpoint in this codebase sends a response body directly today (every download is a presigned S3 URL), so a chunked CSV response is net-new but standard.

**Options considered**:
- A) **Materialize, then send.** Build the full CSV in memory, then send it. Simplest, but peak memory = full CSV on a 2 GB single task, and does not bound the future large report.
- B (chosen) **Stream chunked CSV directly to the client** via `MyXQL.stream` -> `CSV.encode` -> `Plug.Conn.chunk`. Server memory bounded to one batch. Completeness is conveyed by HTTP chunked transfer-encoding: a cleanly-terminated stream = complete file; an aborted/incomplete chunked stream = truncated. The client (cc-data) stages the body to a temp file and renames it to the final name only on clean stream completion, so a truncated download never surfaces as a partial file to the user.
- C) **Async task + poll**, mirroring Athena. Contradicts the ticket's "compute-on-request, no envelope" decision and reintroduces Portal-side run state.
- D) **Stage to a server-side temp file, then serve.** Rejected: server-side staging is unnecessary and streaming to the client is cleaner (no double I/O, no cleanup).

**Decision**: **B, compute-on-request, chunked CSV streamed directly to the client** (no S3 object, no presigned envelope). Server memory is bounded by streaming `MyXQL.stream` batches through `CSV.encode` to `Plug.Conn.chunk`. The "no partial file" acceptance criterion is satisfied at the client boundary: the response is chunked, a clean chunked-EOF signals a complete file and an aborted stream signals truncation, and the client (cc-data) writes to a temp file and promotes it to the final name only on clean completion. On a query/DB error before any bytes are sent, the endpoint returns a clean JSON error; on a mid-stream failure the server aborts without a clean termination so the client discards its temp file. The maximum time a download may run (and thus hold a portal-DB connection/read view) is bounded by the API-specific timeout in the next Open Question. See the cc-data client dependency noted in Out of Scope.

### RESOLVED (Q2): Should the API use a shorter download timeout than the portal DB's 5-minute `@query_timeout`?
**Context**: Because Q1 streams the CSV directly to the client, a portal-DB connection and an open read view on the production portal DB are held for the entire download. The web UI does not have this exposure (it materializes the result and releases the connection before pushing bytes to the browser), so the 5-minute `@query_timeout` (`portal_dbs.ex:9`) is too loose for the streaming API path.

Verified during the decision:
- No HTTP request/idle timeout is configured; the server uses the Bandit adapter (`Bandit.PhoenixAdapter`, `config.exs`; version `1.5.0` pinned in `mix.lock`) and its defaults apply, so nothing at the HTTP layer independently caps a long download.
- For `MyXQL.stream`, `:timeout` bounds each per-batch fetch, not the total download wall-clock. Bounding total download time therefore requires an explicit deadline tracked in the chunk-writing loop, not just a MyXQL option.

**Decision**: **Enforce an API-specific, configurable download timeout for Portal downloads (option B + configurable).** The Portal download path uses:
- an overall **wall-clock deadline** checked in the chunk loop, so total download time (and thus the held connection / read view) is bounded regardless of how many batches stream, and
- a per-batch fetch timeout on the streamed query.

The deadline is **configurable via an environment variable** (e.g. `PORTAL_DOWNLOAD_TIMEOUT_MS`) with a conservative default (proposed 120_000 ms; final value settled in `implementation.md`). When the deadline is hit: if no bytes have been sent yet, return a clean JSON timeout error; if the stream is already in progress, abort the chunked response without a clean termination so the client detects truncation and discards its temp file (per the Q1 contract). This is independent of pool sizing, which is intentionally out of scope.

### RESOLVED (Q3): How is a Portal download recorded in the audit log, and is the write fail-closed before streaming?
**Context**: `data_access_log` is the researcher-data access audit trail. The Athena path records every download via `AuditLog.issue_download_url` (wraps the presign, writes a `download_url_issued` row, fail-closed). A Portal download issues no URL, so the existing function does not fit as-is. Q1's streaming makes the ordering matter: if the audit row must be written before any CSV bytes are sent, a failed audit write returns an error and no download.

Verified during the decision:
- The audit schema (`data_access_log_entry.ex`) has a controlled vocabulary: `event ∈ {download_url_issued, export_scoped, bulk_read, attachment_urls_issued}`, `source ∈ {web, api}`, `data_type ∈ {run_csv, job_result, answers_bulk, history_bulk, export_scoped, attachment}`. `data_type: "run_csv"` and `source: "api"` fit a Portal download; only `event` has no good existing match.
- `event` is a plain string column gated only by `validate_inclusion`, so adding a value is a one-line changeset change with no DB migration.
- `AuditLog.log_attachment_urls/3` (`audit_log.ex:56`) is an existing precedent for a direct, non-presign fail-closed audit write that returns `{:ok,_}|{:error,_}` for the controller to gate on.
- The audit UI renders `data_type / event (source)` verbatim (`audit_log_live/index.html.heex:50`) and filters only by export_id/remote_endpoint, so a new event value needs no UI change.

**Decision**: **A′, audit before streaming, fail-closed, single row, with a new distinct `event` value.** Add a new fail-closed `AuditLog` function shaped like `log_attachment_urls` that writes one `DataAccessLogEntry` with `source: "api"`, `data_type: "run_csv"`, and a new `event` (e.g. `"run_csv_streamed"`, added to the changeset `validate_inclusion` list, no migration). The controller writes this row **before** `send_chunked`/any bytes; on audit-write failure it returns a clean `SERVER_ERROR` and does not stream, matching the Athena path's "audit before the client can access data" semantics. A distinct event value keeps streamed Portal exports distinguishable from presigned Athena downloads in the audit trail. A single pre-stream row is sufficient; no completion row.

### RESOLVED (Q4): Should bulk answers/history/attachments accept every non-tbd Portal run, or only the Student ID Mapping report?
**Context**: The primary use case is the Student ID Mapping run, but loosening the shared `get_api_report_run` gate makes *all* non-`tbd` Portal runs pass the bulk endpoints. Derivation (`LearnerData.fetch`) keys on `cohort/school/teacher/assignment/class/student/permission_form`.

Verified during the decision:
- Three Portal reports (`teacher-status`, `resource-metrics-summary`, `resource-metrics-details`) filter by `[:cohort, :school, :teacher, :assignment]`, all learner-derivable.
- Two aggregate reports (`school-metrics`, `summary-metrics-by-subject-area`) filter by `[:country, :state, :subject_area]`. `LearnerData.fetch` does not read those fields (`learner_data.ex:24`), so its filter is silently ignored.
- Consequence of an ignored filter is bounded by authorization (`apply_allowed_project_ids_filter` always scopes to the caller's allowed projects), so it is never a cross-tenant leak. But it is still a footgun: a project researcher gets *all learners in their projects* (an over-broad, slow pull), and a super-admin (`:all`) gets `{:error, "Cannot run query with no filters"}` -> today a confusing `500`.
- `ErrorHelpers` currently defines 400/401/404/409/410/500 (`error_helpers.ex`); there is no 422 code yet.

**Decision**: **A (uniform gate) plus a per-report `derives_learner_data` capability check.** Every non-`tbd` Portal run still passes `get_api_report_run` (no allowlist, no Portal-awareness in the gate), so aggregate reports remain listable, fetchable, and downloadable. Separately, the bulk endpoints (`/answers`, `/history`, `/attachments`) return a clean **422 `UNPROCESSABLE`** for a run whose report declares `derives_learner_data: false`. This is a per-report capability flag (default `true`; set `false` on the two aggregate reports, `school-metrics` and `summary-metrics-by-subject-area`, whose `include_filters` are geography/subject and never narrow to learners), resolved from the run's `report_slug` in the shared `derive_endpoint_set`, not a per-run filter-shape check and not a slug allowlist. It stays consistent with the ticket's "type-based, no allowlist" principle, replaces both bad behaviors (the silent over-broad researcher pull and the confusing super-admin 500) with one honest response, and keeps the learner-derivable reports (Athena and Portal) and the forthcoming Student ID Mapping run completely unchanged.

Why per-report rather than the originally-drafted per-run filter-shape 422: (1) it is semantically honest, the aggregate reports categorically cannot answer a per-learner request, so the flag says "this report has no bulk learner endpoints," not "your filter is too broad"; (2) it eliminates the `nil`-vs-`[]` "blank" ambiguity that a filter-shape check had to pin down (former R4-2); (3) it collapses the regression/test cost, since the existing bulk/attachment fixtures use learner-derivable reports and stay green as seeded rather than the majority of both suites flipping to `422` (former R4-3); and (4) the two approaches are behaviorally identical for every report that exists today (learner reports are all-learner-filtered, aggregates all-geography). Cost: add `422` (and `503`) to `ErrorHelpers`, one struct field plus two `tree.ex` edits, a multi-headed check in `derive_endpoint_set`, and a tree-consistency test so a future aggregate report cannot silently miss the flag (see Technical Notes: Bulk endpoints). Note: this changes the two aggregate reports' behavior on the bulk endpoints to a `422` for *all* roles, not just the super-admin case; their download/list/show are unaffected.

The spec enumerates the endpoints powered by the shared `get_api_report_run` gate as show, `/download`, `/answers`, `/history`, and `POST /attachments` (Background line 22; Listing/Download/Bulk requirements). - `GET /api/v1/reports/:id/jobs/:job_id/download` -> `Reports.get_api_report_run` (`report_job_controller.ex:31`)

Both are wired in the router (`router.ex:69-70`) inside the same `:api_authenticated` scope. Because they share the exact gate the story widens from `Tree.athena_report_slugs()` to `Tree.api_report_slugs()`, a Portal run id that is `{:error, :not_found}` today will pass the gate and reach `ReportJobController` once the gate opens. The net observable change (`/jobs` -> `200 {items: []}`) is benign, but it is currently **accidental and unspecified**: it is a side effect of `list_jobs(nil)` returning `{:ok, []}`, not a decision the spec made, and it has no regression coverage. A reader of the spec would conclude, wrongly, that the gate widening touches exactly five endpoints. #### RESOLVED: R5-2 - The Portal-download pre-stream error path must also cover `get_query`/`update_query` returning `{:error, "Cannot run query with no filters"}`, which is reachable before any SQL runs
**Resolution:** The Download requirement now defines "before any bytes are sent" as covering both the query-*building* failure (`get_query`/`update_query` `{:error, _}`, including the `"Cannot run query with no filters"` short-circuit) and the query-*executing* failure, both mapping to the same clean JSON error and neither allowed to raise a `WithClauseError`/out-of-contract `500`. The Portal-download-execution Technical Note spells out matching both build steps' `{:ok, _}` before opening the stream, and notes the `"Cannot run query with no filters"` string is an app-level constant exempt from the SEC2 leak concern. The Tests "failure before the first byte" bullet now has two variants (execution error and construction error), with the construction case exercised by a super-admin blank-filter run.
The Portal-download Technical Note (line 75) describes query construction as `report.get_query.(report_run.report_filter, report_run.user)` -> `ReportQuery.get_sql/1,2` and then `MyXQL.stream`, framing the "failure before any bytes are sent" case (Download requirement; Tests bullet "query error before the first byte") as a DB/query execution error, and SEC2 scopes error-hiding to raw `MyXQL`/`DBConnection` messages. Verified a distinct, earlier failure mode that is not an execution error and not a DB message: every Portal report's `get_query` ends in `ReportQuery.update_query/2`, which returns `{:error, "Cannot run query with no filters"}` when the assembled `join` and `where` are both empty (`report_query.ex:43-44`). This is reachable for a super-admin (`get_allowed_project_ids -> :all`, so `apply_allowed_project_ids_filter` adds no scoping) running a Portal report with a blank filter and no dates: `teacher_status_report.ex:47-103` then produces `join: [], where: []` and `update_query` short-circuits to that error before `get_sql`/`MyXQL.stream` are ever called (the web LiveView hits the identical error via `get_row_count`/`run_report`, so such a run is already non-functional in the UI - the API must not treat it any worse).

Why it matters: the download implementation must map a `{:error, _}` from the `get_query` **or** `get_sql` step (before the stream opens) to the same clean pre-stream JSON error as an execution failure, not let it fall through as an unhandled `WithClauseError` (-> a raised `500` in a shape the API contract does not define). This is arguably implied by "a failure before any bytes are sent returns a clean JSON error," but the Technical Note and Tests bullet only name the execution-time DB error, so the earlier `get_query`-time error is easy to miss in implementation. Note this particular message ("Cannot run query with no filters") is an app-level constant, not a raw DB string, so it is safe to surface or to genericize; SEC2's leak concern does not apply to it.

Suggested resolution: reword the Portal-download Technical Note and the "query error before the first byte" test bullet to cover a failure at **either** the `get_query`/`update_query` step or the streamed-execution step (both pre-first-byte -> clean JSON error), and add a test for a blank-filter super-admin Portal run asserting the clean pre-stream error rather than a raised `500`.

**Decision**: "Before any bytes are sent" covers both pre-stream failure modes: the query-*building* failure (`get_query`/`ReportQuery.update_query` returning `{:error, _}`, including the `"Cannot run query with no filters"` short-circuit a super-admin blank-filter run reaches) and the query-*executing* failure (a DB error on the first fetch). Both map to the same clean JSON error; the download path must match both build steps' `{:ok, _}` before `send_chunked`, and neither may fall through as an unhandled `WithClauseError`/`500`. The Download requirement, the Portal-download Technical Note, and the Tests "failure before the first byte" bullet (two variants) were updated. Confirmed statically (and reaffirmed while building the Round 6 probes) that `get_query` returns the `{:error, _}` tuple rather than raising: `TeacherStatusReport.get_query` tails into `apply_filters -> ReportQuery.update_query`, which returns `{:ok, _} | {:error, _}` (`report_query.ex:43-44`), so the clean pre-stream error path is reachable without a `rescue`.

### Senior Engineer / API Contract Reviewer

#### RESOLVED: R6-1 - The "empty result -> header-only CSV" contract contradicts the "byte-compatible with the web CSV" contract, because the web encoder emits an *empty* body for zero rows
**Update (Round 7, project-owner decision):** rather than accept a permanent web/API divergence, the web `format_results/2` empty-body output was identified as a pre-existing bug and is corrected in this story to emit the same header-only line as the API. The header-only-for-empty contract stays; the divergence is resolved by fixing the web side, so byte-compatibility now holds for the empty case too (both header-only) and is no longer scoped to non-empty results. The implementation plan's shared-encoder step carries the web-side fix and adds a LiveView empty-download test. The original Round 6 decision (keep the divergence, scope byte-compat to non-empty) is retained below as the decision log.

**Decision (Round 6, superseded by the Round 7 update above)**: Keep the header-only-for-empty contract (SE1) as a **deliberate, documented divergence** from the web CSV, and scope the byte-compatibility contract to **non-empty** results. The byte-compat requirement, the zero-row requirement, the Portal-download Technical Note, and the two Tests bullets (download-success and empty-result) were all updated to state this explicitly rather than assert both incompatible properties at once.
Verified empirically (T1): the web LiveView's `format_results/2` builds its CSV via `CSV.encode(headers: atoms, delimiter: "\n")` over the mapped rows (`show.ex:208-216`); against a live MySQL 8.0 this encoder emits an **empty string** (zero bytes) for a zero-row result, *not* a header line. So "byte-compatible with the web CSV" (Download requirement; SE2/SE4) and "zero rows returns a header-only CSV" (Download requirement; SE1; Tests) are mutually exclusive **for the empty case only**. Chosen resolution (b) over (a) "match the web = empty body": a header-only file is unambiguously a valid empty result, whereas a zero-byte body is indistinguishable from the failed/truncated transfer the streaming contract already forces the client to guard against (see R6-3), so header-only is the safer client contract; the cost is one explicitly-documented exception to byte-equality. The header line is producible from `MyXQL.stream`'s leading zero-row envelope, which carries `columns` (confirmed in the same probe). This is a contract choice a project owner may override to (a) if strict web/API byte-equality is preferred over the empty-file disambiguation; flagged in chat.

#### RESOLVED: R6-2 - The byte-compatible streaming-CSV encoding recipe was doc-derived, not empirically confirmed; the exact recipe is now pinned
**Resolution:** The Portal-download Technical Note and the download-success Tests bullet now state the exact recipe, confirmed byte-identical to `format_results/2` in the T1 probe.
Verified empirically (T1) against live MySQL 8.0: the envelope shape matches the myxql docs exactly - a leading `num_rows: 0` result carrying `columns`; a trailing `num_rows: 0` result iff the row count is divisible by `max_rows`; and *two* zero-row envelopes for a zero-row query. The recipe that produced bytes **byte-identical** to `format_results/2` for a non-empty result (including CSV quoting of values containing commas, embedded double-quotes, and newlines): emit the header once as a single CSV-encoded row of the column-name strings, then encode each non-empty batch's raw `MyXQL` row lists as list-of-lists (not remapped to maps), all with `delimiter: "\n"`, skipping every zero-row envelope. The naive `CSV.encode(headers: ...)` per batch was confirmed to repeat the header row mid-file (the exact SE4 hazard), and is rejected.

### QA Engineer / DevOps Engineer

#### RESOLVED: R6-3 - The Bandit mid-stream truncation mechanism (the whole "no partial file" contract) was assumed, not tested; now confirmed, with a status-code caveat the spec had not stated
**Resolution:** The failure-mid-stream Tests bullet now records the confirmed Bandit behavior and the `200`-status caveat.
Verified empirically (T2) against a real Bandit endpoint: a plug that raises after N `chunk/2` calls closes the socket **without** the terminating `0\r\n\r\n` chunk, and a chunked-aware client detects it (`curl` exits `18`, "transfer closed with outstanding read data remaining"), whereas a cleanly-completed stream ends in `0\r\n\r\n` and exits `0`. This confirms the Q1 "no partial file" mechanism holds on Bandit specifically (not just in principle) and confirms R3-B2 (the property is invisible to `Plug.Test`, so it belongs in an integration test against a live Bandit socket - the T2 harness is effectively that test). New caveat the spec had not made explicit: the response status is already `200 OK` when the mid-stream failure occurs (headers flush at `send_chunked`), so a client **cannot** rely on the HTTP status to detect a truncated download and must key on chunk-framing completion - which is precisely why the cc-data client stages to a temp file and promotes only on clean EOF (Out of Scope). Added to the failure-mid-stream Tests bullet.
